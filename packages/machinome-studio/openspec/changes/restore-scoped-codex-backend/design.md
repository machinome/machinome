## Context

Studio 0.1.0 is private, experimental and unpublished. Claude is the profile default; OpenCode is explicit selection only. ADR 0025's retirement is an accepted decision, not an implementation accident. Its exact-authority principle survives; ADR 0032 below proposes superseding the retirement because new measured controls satisfy that principle. ADRs 0006, 0017, 0018, 0022, 0023 and 0026 establish the backend seam, project-owned selection, multi-backend ownership, pristine replacement, idle model mutation and no permission bypass.

The carried spike `docs/spikes/codex-tool-isolation/` measured installed `codex-cli 0.157.1` on Linux. Its 23 deterministic forced-call cases inspect the actual outbound model tool registry; four authenticated cases establish Sol/Astra interoperability and guarded restart/resume. Plain resume restores native patching. The successful route therefore sends `environments: []` at thread creation AND every turn start, controls model metadata, disables native tool features and uses client-executed dynamic tools. Context7 `/openai/codex` source confirms persisted dynamic tools on resume, but provides no production exact-registry attestation API. Installed experimental schema and spike evidence govern this version's concrete contract.

## Goals / Non-Goals

**Goals:** restore explicitly chosen Codex roles through `AgentBackend`, preserve exact profile tools and skill announcements, use the measured file-backed login without configuration inheritance, make unsupported capability failures actionable, and cover full delivery/tool/lifecycle behavior with mock and authenticated evidence.

**Non-Goals:** Codex defaults or profile runtime tables, model/provider substitution, arbitrary operator configuration, keyring/API-key/custom-provider support, library research tools, global role adapters, backend-neutral executor hardening, OS isolation of CAD, persistent floor conversation recovery across Studio restart, framework changes or publication. The librarian's existing unavailable research surface stays unavailable.

## Decisions

### 1. Qualify a narrow contract before starting project work

Initial supported matrix: Linux, exact `codex-cli 0.157.1`, `gpt-6-sol` and `gpt-6-astra`, OpenAI provider, freshly provisioned Studio-owned file-backed Codex login. Do not infer that later versions, old GPT models or other bundled models work. Reasoning choices are the intersection of reviewed model metadata and the installed schema; a missing/unsupported effort is an error. Omitted effort uses the existing profile effort, validated for the chosen model. Additional support needs new evidence and an explicit contract update.

Version text alone is insufficient. Resolve and retain the actual executable, including its real binary if the executable is a package shim; fingerprint the executed artifacts, validate the experimental app-server schema fields used by the adapter and validate the supported bundled models' relevant metadata against the reviewed fixture. Build a private controlled catalogue from those reviewed entries only: `tool_mode = direct`, no `multi_agent_version`, empty `experimental_supported_tools`, preserving model identity and other reviewed metadata. Never use cached remote metadata to expand supported choices.

Before preparation or real role sessions, run a bounded credential-free local-provider capability probe using the SAME resolved binary, private runtime policy and catalogue as production. It creates synthetic threads with each actual role's dynamic tool names/schemas and an empty-tool role, inspects actual outbound tools including namespace wrapping, forces undeclared/native execution calls, tests later turns, model changes and guarded restart/resume, and checks filesystem sentinels. An unknown registry, executable/schema/catalog mismatch, timeout, managed-config conflict or failed rejection test makes Codex unavailable. Cache a success only for this Studio process and the exact artifact/config/catalog/tool-schema fingerprints; changed content invalidates it. Check fingerprints again at actual launch. Fingerprints identify tested local content, not cryptographic vendor authenticity: the installed executable is trusted operator software. This probe starts only temporary qualification processes and writes synthetic temp state; no project is prepared and no authenticated role exists yet.

Inspect effective configuration and configuration provenance through the pinned app-server's supported read endpoints/schema BEFORE creating any thread that could initialize inherited MCP/hooks. A private HOME does not remove system or enterprise layers. Confirm the pinned runtime's table merge semantics; an empty table override is not assumed to remove inherited entries. Reject unexpected MCP, plugins, hooks, tool/environment features or managed restrictions that conflict with the required policy; do not override enterprise restrictions. If effective policy cannot be established before possible inherited execution, refuse launch. Validate schema support and effective values rather than ignoring warnings. Runtime events showing a native execution item, environment attachment, model reroute or unexpected server request are violations: deny requests, stop the affected runtime and report failure. Event filtering is defense in depth, never the readiness proof.

There is no claimed per-turn production registry attestation. The practical proof is a locally measured exact binary/config/model contract plus immutable inputs and fail-closed dispatch. A compromised executable or operator can defeat a local harness; this adapter is not a security boundary against them. Do not intercept authenticated model traffic to inspect it.

Alternatives: trusting flags/version alone fails the spike; an inherited catalogue advertises collaboration/code-mode tools; a model refusal is not enforcement; shipping a broader assumed version range loses the evidence.

### 2. Keep configuration, instructions and authentication separate

Own mode-0700 private HOME/XDG runtime directories and an unrelated neutral working directory, never the project root. CODEX_HOME is the dedicated durable Studio home, not the operator home or a per-project copy. Allow only the minimal known process/network-certificate variables. Explicitly withhold API-key/provider override, proxy-injected configuration, role adapters and inherited MCP/plugin/project settings. Configure read-only sandbox and `approvalPolicy = never`, web disabled, the spike's disabled feature set, experimental user-input and plan tools disabled, controlled catalogue and experimental API. No `danger-full-access`, bypass, automatic approval or permission-disabling flags.

The pilot accepted a separate one-time Studio Codex login using the existing subscription/account; normal CLI credentials stay untouched. Add a dedicated setup/login command (for example `python -m floor.codex_auth login`) that resolves the explicit Studio-owned durable state path, creates mode-0700 storage, checks its exclusive ownership lease and invokes the qualified CLI's ordinary `login --device-auth` with `cli_auth_credentials_store = file`. Interactive login is an operator provisioning action, never performed by project open or setup as a side effect. Its output may show the vendor verification URL/code but never credential contents. Missing login produces an actionable command to run. Reject API-key, keyring and custom-provider modes initially. Do not copy tokens from normal operator auth, use the internal-only external-token API, or treat `--with-access-token` as OAuth interchangeability.

Use that dedicated persistent CODEX_HOME directly as the single authoritative native auth store: Codex-managed refresh updates its own auth.json there, not a discarded copy or symlink target. Preserve durable authentication across project close and hub shutdown. Native login/refresh account semantics remain vendor behavior; test app-server auth reads, recovery and refresh storage with deterministic fixtures and a real fresh Studio login. Expired/revoked login reports re-login guidance with no fallback. Login/logout/provisioning requires the same exclusive lease as the running service, so an operator stops the hub before replacing its auth. Normal operator auth/config is never read or written.

Because CODEX_HOME owns configuration and thread state as well as auth, make the entire dedicated home Studio-owned, with a minimal generated/validated config and strict no-extras hygiene. Retain only the documented native credential state and Studio-managed files; reject unexpected config, MCP, plugins, hooks or instructions rather than importing them. Keep HOME/XDG homes and neutral cwd private, and check effective system/enterprise provenance before any thread starts. Schema/config verification precedes authenticated login state checks. Credentials remain absent from arguments, logs, activity, evidence and catalogue fingerprints. Use the concrete stable default `${XDG_STATE_HOME}/machinome-studio/codex` when XDG_STATE_HOME is an absolute path, otherwise `~/.local/state/machinome-studio/codex`, resolved once from the operator environment by hub/auth composition before constructing private child environments. The provisioning module and runtime use the same resolver; no divergent `--home` or per-project auth-source override.

### 2a. One authenticated service supports concurrent projects

A hub-owned Codex service owns exactly one authenticated app-server and its authoritative auth home. Project-specific CodexBackend adapters implement the existing portable seam and borrow that service through a narrow injected manager; each still owns only its project role handles, MCP workers and event iterator. The SessionRegistry-owned manager is supplied by hub/session composition, never a process-global singleton guessed from cwd. Single-floor entry points construct the same manager for their own lifetime. Acquire an exclusive advisory process/file lease for the durable home during selected-Codex preflight, before viewer resolution or project preparation, as well as before app-server/login start; cancellation before a Session exists releases the pending lease/reference. A second distinct hub using it fails with an actionable ownership reason, while simultaneous projects in one hub share the owner normally.

The manager lazily starts the service after credential-free qualification, reference-counts project adapters, and registers an immutable thread-to-adapter/project/role mapping. The single app-server reader routes known events/callbacks to that adapter only; unknown threads never fall back. Ownership keys use opaque handle/thread identity, not role alone: pristine replacement may briefly hold two handles for the same role, and the old handle stays authoritative until atomic swap succeeds. Adapter close rejects and drains its callbacks, ends its threads and workers, unregisters them and drops its reference. It cannot terminate another project's app-server or delete another project's state. Last-reference release stops the service boundedly; the hub manager's final close is idempotent and releases the lease. Serialize start/stop/refcount transitions to avoid a new borrower racing final close. Hold the lease while login/native refresh/processes can access auth; never create independently rotating authenticated copies. Bounded cleanup is cancellation-safe and retryable: a cancelled close retains ownership/lease until reap finishes, never marks unreleased resources closed or deletes shared state underneath live work.

Shared app-server failure fans out role-scoped failure to every attached Codex role; unrelated Claude/OpenCode owners and projects remain alive. This deliberately uses the existing role recovery channel rather than emitting backend_failed that would end each mixed-backend run. Closing one failed project cannot restart the shared service under another project's handles. Registry-owned recovery serializes service-generation transitions and coordinates retained sibling handles. New envelope recovery/reacquisition uses a single coordinated service generation and rejects stale thread/turn/callback IDs. A service restart resumes known retained threads with their immutable registry, reapplies empty environments to every new turn and never replays context. If all borrowers close, project conversations end as already specified.

Durable auth is distinct from ephemeral floor sessions: thread records created in the durable CODEX_HOME are Studio-owned temporary conversation state, deleted with the pinned `thread/delete` API through verified native cleanup when each project closes, with a small Studio-owned registry enabling cleanup of orphaned threads on next startup. Do not delete unrelated native state or auth; no conversations are reopened as floor sessions after a hub restart. Retain app-server thread records only while needed for coordinated in-hub process recovery. Update both architecture and tests for this shared ownership rather than pretending the process still belongs exclusively to one project.


Each thread receives the exact profile prompt, role identity, active project/model facts, and skill names/descriptions with its dynamic load-skill tool. Project-root `AGENTS.md`, if carried, is manually read only when regular/non-symlink and framed as subordinate guidance; Codex gets no project cwd or automatic ancestor discovery. Tool arguments/results and profile instructions are the only project data conveyed to Codex.

### 3. Dynamic tools call the existing owned floor subprocess

One Codex adapter owner per project session borrows the hub's shared authenticated app-server service. Each role owns an independently launched floor MCP subprocess rooted at its verified project/model, injected with floor URL/session and ONLY its declared skill registry. The app-server is not given that MCP server: the adapter initializes it, obtains authoritative tool descriptions/schemas, selects exactly `session_tool_names(...)`, and advertises corresponding unambiguous dynamic names (for example `floor_read_file`) to Codex. Keep one immutable bijection to the canonical floor names; no suffix/alias matching. Tool schemas come from the existing floor definitions, never a second manually maintained inventory.

For every `item/tool/call`, validate request shape, dynamic namespace/name, JSON object/schema (namespace is nullable and vendor arguments are unconstrained JSON; adapter validation is authoritative), owning thread, current native turn and portable delivery, live opaque floor session and non-closing handle. Reject unknown/stale/cross-role calls before contacting MCP. Do not run `ProjectTools` in the event loop or `asyncio.to_thread`: those synchronous methods spawn subprocesses and could outlive cancellation. A per-role queued MCP request task preserves ordering while the app-server reader continues processing steering/events. Validate broker sender/role equals the thread's injected role (including acknowledge/complete); reject mismatch and use that trusted value in the forwarded arguments. Do not allow model-chosen floor URL, session, skill registry or execution root. This Codex bridge check is scoped to its new dynamic dispatch and does not claim to repair every backend's executor authority.

Translate MCP text/structured output to Codex `inputText` and image blocks to `inputImage` data URLs using the installed experimental schema. Preserve error status in `success: false` with useful bounded error text; tool failures are model-visible results, not automatically role failures. Unsupported result types fail explicitly. Image bytes must reach inference, not just a browser path. Preserve running/terminal tool activity with one role/item key, bounded summaries, optional path/diff from floor operations and actual vendor token usage; no raw credentials, transport frames or unbounded image/base64 details enter activity.

Own the MCP worker process group so close stops its blocking Git/build/snapshot command descendants as well as its parent. Reject new callbacks first, cancel and await callback tasks, interrupt/archive threads boundedly, stop workers and descendants with TERM then KILL and reap, release its shared-service reference; the final service owner stops app-server and removes ephemeral state last. Durable Studio authentication is retained. Completion of close means no owned command can still mutate the project; it does not undo a mutation already completed. Test a slow fixture child writes no marker after close. This is lifecycle ownership, not OS sandboxing of hostile code.

### 4. Preserve existing delivery and mutation semantics

No warm-up inference is needed: creation carries instructions and dynamic tools. `deliver_start` starts a turn with empty environments plus selected model/effort and returns its correlation identity. `deliver_steer` targets only the expected active turn; a completion race raises `InactiveTurn`. `deliver_notice` is steer-only, returns false on completion race and never starts/replaces a turn. Steering retains portable delivery identity. No arbitrary turn creation from native/server requests.

Normalize only known thread/turn items. Emit a nonempty completed agent message once per item as `role_message`, never delta text or an invented empty final response; an empty-text/tool-only turn still emits its correlated completion. Native errors/failed turns emit role failure; cancellation during intentional close is terminal cleanup, not renewed standby. Unknown/late events cannot complete newer work. Duplicate events/results are idempotent, and replayed callbacks do not repeat mutations.

Idle `update_runtime` changes model/effort for later guarded turns on the same thread; fresh catalogue exposes only qualified supported OpenAI choices. Used roles cannot migrate backend/provider. Pristine replacement and persisted TOML rollback use the existing orchestrator lock and commit order. Report Codex's provider separately as OpenAI in Agents while keeping its internal single-provider selection grammar. Missing qualification/auth disables the Codex catalogue with a reason, without breaking a Claude-only floor. Preserve a per-backend unavailable-reason map (or equivalent structured status) alongside available choices through orchestrator/routes/UI; current aggregation must not drop Codex's reason merely because Claude choices exist. Explicit project Codex selection fails preflight before preparation; a later authentication/model-access failure unwinds started resources according to existing open semantics. Account-level access is not guaranteed by bundled metadata; a model denial must be surfaced honestly.

Process restart/resume is service-coordinated recovery inside the dedicated service's retained native thread state, not conversation migration. Resume restores the original dynamic registry; validate persisted metadata against the immutable role registry, and ALWAYS send empty environments on the first and every subsequent turn. If resume cannot be established safely, fail and require the existing explicit recovery/reopen path instead of replaying context. The shared owner's transport death uses the role-scoped fanout described above; unshared backends retain their existing semantics.

### 5. Validate a coherent cycle and record the decision

One cycle keeps restoring selectability coupled to proven scoping and coordinated auth ownership. Use two sequential implementation/review checkpoints: first qualify the shared service/auth lifecycle and cross-project routing/teardown, then restore selectable adapters/UI and perform full live validation. The ownership work exists solely to serve this immediate restoration need; it is not a standalone speculative capability. Red-first tests cover parser/defaults, preflight failures before preparation, exact dynamic registries, delegated sender rejection, real image transport, independent roles, restart/steering/notices/model updates, tool errors, duplicate/late/empty output, partial open and hung-child teardown. Deterministic qualification runs the actual installed binary with no model credentials. Authenticated integration uses synthetic independent project fixtures and the separately provisioned Studio login: a direct Builder, at least Foreman and Machinist delegated lifecycle, image inspection, active steering, model switch and restart. Browser inspection captures Codex provider/model choices, valid gating, normalized activity and failure display. Record versions, exact tested content and limitations without credential or raw-request retention.

On implementation completion promote ADR 0032, update ADR 0025 status and relevant amendment indexes, rewrite affected overview/README/contract passages, sync these spec deltas and archive. Do not claim restored portability or publication.

## Risks / Trade-offs

- Experimental protocol and model-tool metadata can change → exact version/model qualification, reviewed fixtures and actual forced-call tests; unsupported changes refuse launch.
- Qualification adds startup latency and requires loopback access → bounded credential-free probe, cache only unchanged inputs within one Studio process; expose the reason if blocked.
- Shared OAuth credentials can rotate concurrently → one native authoritative Studio store and exclusive service/login lease; no copied operator refresh tokens.
- No live production registry attestation exists → state the narrower proof, never present event suppression as containment, refuse unknown effective configuration.
- Floor tools still execute host CAD/Git/build code → owned cancellable subprocess lifecycle only; broader containment remains separately deferred.
- User-namespace sandbox failure on this host → no claim of OS sandbox enforcement; no-environment tool registration is the measured boundary and read-only settings a backstop.
- Supported model metadata does not prove account entitlement → honest access errors with no fallback; live smoke is evidence for the tested account only.

## Migration Plan

Existing Claude/OpenCode projects keep their selection and defaults. Operators install the qualified Codex version and complete the dedicated Studio login before explicitly selecting `codex:gpt-6-sol:medium` or `codex:gpt-6-astra:medium`. Failed qualification leaves Codex unavailable and offers the existing supported backends. Reverting the implementation restores retirement and rejects Codex selections; never silently rewrite project files. Integration and publication remain the pilot's separate decisions.

## Open Questions

The pilot resolved authentication: a separate one-time Studio login on the existing account, normal CLI credentials untouched, one shared authenticated owner preserving concurrent projects. No additional consequential choice is outstanding. Exact configuration provenance, native thread cleanup and image response encoding must be confirmed against 0.157.1 during red-first implementation; if the installed API cannot support these contracts, return evidence for design revision. Keyring/API-key support and broader host containment remain deferred work.
