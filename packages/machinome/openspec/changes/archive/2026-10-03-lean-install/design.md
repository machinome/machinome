## Goals / Non-Goals

**Goals:**

- Every leaf at `machinome.node.<x>`, the root spellings unchanged, the old
  dotted paths refused naming the new ones.
- A bare install with no CAD kernel; one extra per kernel module, named by its
  address; every kernel module refusing its absent kernel at import with the
  install line, at each of the three doors: a leaf module import, the root's
  lazy export, the CLI command.
- The markings reducer and the `import-step` reader reached through seams.
- No change for a project with its extras installed: same results, artifacts
  and messages; the suite unchanged with every extra installed.

**Non-Goals:**

- No package cut, no repository, no satellite (layer 2).
- No root cleanup: the root keeps re-exporting every name it does today.
- No OpenSCAD change (cycles 5 to 8).
- No upgrade of any kernel pin; the coupling stays.
- No suite reorganisation by future package and no lean CI job (deferred by
  the pilot as not architecture).

## Decisions

### 1. The addresses, and where the sheet node lives

`machinome/node/adapters/<x>.py` → `machinome/node/<x>.py` for `cadquery`,
`build123d`, `step`, `molejo`, `solid2`, `openscad`, `jscad`, `stl`, by
`git mv`, with intra-package imports rewritten (`machinome.node.adapters.cadquery`
→ `machinome.node.cadquery` in `step.py`). `_EXPORTS` keeps every key; its
values lose `adapters.`.

**`Build123dSheetNode` joins `Build123dNode` in `machinome.node.build123d`**;
`adapters/build123d_sheet.py` is folded in (its `_PLANE_TOLERANCE`,
`_export_dxf` and the class; no name collides with `build123d_shape` or
`Build123dNode`). The SVG reducer joins them (Decision 8). Reasons:

- **The table as ratified** puts `Build123dNode`, `Build123dSheetNode` and the
  SVG reducer at `machinome.node.build123d`, installed by
  `machinome[build123d]`, distributed as machinome-node-build123d.
- **"Node type" in the norm is the technology, not the class.** The same table
  puts `StepNode` and `StepAssembly` in one module; the plan's "one package
  per node type" means one per kernel front end: one dependency, one pin, one
  licence, one release. The sheet node has the same kernel, pin and licence as
  `Build123dNode`.
- **Rule 2 needs no lookup.** A module `machinome.node.build123d_sheet` would
  either need an extra `build123d_sheet` installing exactly what `build123d`
  installs, or break "the extra is the last component of the address".
- **Types stay distinct.** Two classes in one module are two types
  (`node-model`, "Leaf adapters are distinct types"; a scenario is added).

Rejected: a module `machinome.node.build123d_sheet` (an extra or a lookup for
nothing, and a second package at the cut for the same kernel); a package
`machinome/node/build123d/` with submodules (a node package is one module under
the plan's satellite layout). The plan's "Import paths" table needs no change;
task 9.3 records the decision beside it.

Cost: `machinome/node/build123d.py` grows to about 300 lines (84 + 117 + the
reducer's ~90).

### 2. The former addresses: the dissolved package refuses

`_MOVED` cannot refuse a dotted module path. Probed on 3 October 2026 with a
scratch package whose root defines `__getattr__`: `from pkg.node.adapters.cadquery
import X` never consults the parent's `__getattr__`; the import system asks the
path finders and raises Python's own `ModuleNotFoundError: No module named
'pkg.node.adapters'`. No root name moves in this cycle, so `_MOVED` gains no
row.

The equivalent for a dotted path: `machinome/node/adapters/__init__.py` stays,
holding only its licence header, a docstring, and

```python
raise ImportError(
    "module 'machinome.node.adapters' was dissolved: each leaf type is now "
    "one module under 'machinome.node', so 'machinome.node.adapters.<x>' is "
    "'machinome.node.<x>' ('build123d_sheet' is part of "
    "'machinome.node.build123d'). Write, for example, "
    "`from machinome.node.step import StepAssembly`.")
```

Every module under it is deleted. Probed with the same scratch package: `from
pkg.node.adapters.cadquery import X`, `from pkg.node.adapters import step` and
`import pkg.node.adapters.step` each raise that `ImportError`, because the
parent package is imported first. Attribute access `machinome.node.adapters`
reaches it through `_submodule` and `_load`, which splices the requested name
into it; that is accepted (the message still names the new address).

Why not a plain `ImportError` naming the exact submodule: the package cannot
know which submodule was asked for without an import hook, which the plan
rejects (Flask's `flask.ext`). Why not Python's own error: it names the old
package and not where the names went, against the root's rule for moved names
("the message it gets names where the name went"). Why not nine one-line
modules each naming its new home: nine files kept only to refuse, where one
suffices. The message names `machinome.node.adapters` and, deliberately, no
old dotted submodule path, so the universe sweep classifies it by the package
row of the moved-names file. The refusal is kept as long as `_MOVED` is; the
root cleanup decides both.

### 4. The kernel check, one helper, no table

New module `machinome/extras.py`, importing only `importlib.util`:

```python
class ExtraUnavailable(ModuleNotFoundError):
    """A module needs a kernel its extra installs, and it is not installed."""
    def __init__(self, extra, needed_by, missing):
        super().__init__(
            f'{needed_by} needs {missing}, which is not installed; install '
            f'it with \'pip install "machinome[{extra}]"\'', name=missing)
        self.extra, self.needed_by = extra, needed_by

def require_extra(extra, needed_by, *modules):
    for module in modules:
        if not _found(module):
            raise ExtraUnavailable(extra, needed_by, module)
```

`_found(name)` is `importlib.util.find_spec(name) is not None`, a
`ModuleNotFoundError` raised by a finder counting as not found (the tests'
`sys.meta_path` blockers raise it) and a `ValueError` (a loaded module without
a spec) as found. It never imports the kernel, the shape of
`_verdict_store._distribution_token`. Sphinx's `autodoc_mock_imports` installs
a finder that answers a spec for every mocked kernel, so the documentation
build, which installs no kernel, passes the check *(inferred from Sphinx's
`_MockFinder`; the docs job of task 8.6 verifies)*.

Each kernel module calls it first, before any kernel import and before
importing another kernel module:

| module | call |
|---|---|
| `machinome/node/cadquery.py` | `require_extra('cadquery', 'machinome.node.cadquery (CadQueryNode)', 'cadquery')` |
| `machinome/node/build123d.py` | `require_extra('build123d', 'machinome.node.build123d (Build123dNode, Build123dSheetNode, the Svg artwork reducer)', 'build123d')` |
| `machinome/node/step.py` | `require_extra('step', 'machinome.node.step (StepNode, StepAssembly)', 'cadquery', 'OCP')` |
| `machinome/node/molejo.py` | `require_extra('molejo', 'machinome.node.molejo (MolejoNode)', 'molejo', 'OCP')` |
| `machinome/occt/engine.py` | `require_extra('occt', 'the exact engine (machinome.occt.engine)', 'OCP')` |

The engine's call makes it import a second core module beside
`machinome.exact_engine`, which the `occt-engine` requirement "The engine
imports the kernel and nothing above it" forbade; the delta admits
`machinome.extras`, a leaf of the core with no framework import of its own. At
the cut machinome-occt requires cadquery-ocp, so the check never fires there
and may be dropped with the move.

So a refusal reads, for example: `machinome.node.cadquery (CadQueryNode) needs
cadquery, which is not installed; install it with 'pip install
"machinome[cadquery]"'`, in the wording the engine's seam already uses
("install it with 'pip install \"machinome[occt]\"'").

- **A `ModuleNotFoundError`, `name` the missing kernel.** Code that catches
  `ModuleNotFoundError` behaves the same in layer 1 (module present, kernel
  absent) and layer 2 (satellite absent); `name` is the module that is in fact
  missing.
- **The extra is data on the error**, so the CLI and the markings seam answer
  by it without a second copy (Decisions 7, 8).
- **Presence, not import.** Importing cadquery to check it would cost 3.1 s
  where `CadQueryNode`'s module has deliberately imported none since
  `exact-engine` (pinned by `test_node_lazy_exports.py`). A kernel found and
  broken reports its own error where it is really imported.
- **Open/closed.** The module states its extra and kernels; no core table
  learns them. The test of task 2.6 pins rule 2: each call's extra equals the
  last component of its module's address (the package's for the engine).
- Rejected: a table in `machinome.extras` mapping modules to extras (a row per
  node type, which the pilot accepted only for the extras metadata); refusing
  later, at render or materialization (the brief's "refused at import", and an
  error far from the import line that needs the extra); an import hook.

### 5. The three doors

- **A leaf module import** (`import machinome.node.step`,
  `from machinome.node.cadquery import CadQueryNode`): the module's own
  `require_extra` raises `ExtraUnavailable`, naming its node types and the
  extra.
- **The root's lazy export** (`from machinome.node import StepNode`): `_load`
  gains `except ExtraUnavailable: raise` before its `except ImportError`
  splice, so the refusal arrives unmodified. Today the splice treats every
  `ImportError` as a broken install and appends "(raised resolving
  machinome.node.StepNode from .adapters.step)"; an absent extra is not
  broken, and its message already names the node type. It stays an
  `ImportError`, never an `AttributeError`, so `from ... import` carries it and
  `hasattr` raises it, as for a broken backend (the `_MOVED` comment's reason).
  `from machinome.node import *` therefore refuses at the first absent extra in
  a lean install; no project or doc page star-imports the node package (grep,
  3 October 2026).
- **The CLI command** (`machinome import-step`): Decision 7.

`test_node_lazy_exports.py` pins today: the export table and identity; that
naming `StepNode` imports cadquery and OCP and naming the other exact exports
does not; and, under its `CADQUERY_ABSENT` blocker, that a missing cadquery
reached through `StepNode` raises an `ImportError` naming `cadquery` and
`StepNode`, also through `hasattr`. After: `EXPECTED_EXPORTS` targets move to
`machinome.node.<x>`; `test_a_resolved_export_is_a_real_class_not_a_proxy`
imports `CheckCQEditor` from `machinome.node.cadquery`; the submodule probe reads
`cadquery` in place of `adapters`; the blocked-cadquery tests now assert the
refusal (its type, `name == 'cadquery'`, the install line `machinome[step]`,
no "raised resolving" splice), and a new blocker whose `find_spec` returns a
spec whose loader raises `ImportError('broken cadquery')` keeps the
broken-backend pin (spliced, naming `StepNode`). The docstring's "cadquery is a
required dependency and stays one" is corrected.

### 6. The exact engine seam treats an absent OCCT binding as absent

Once `cadquery-ocp` is optional, `machinome.occt.engine` exists in every install
while `OCP` may not. Today `exact_engine()` would report that as a broken
engine (`_absent` accepts only a `ModuleNotFoundError` naming `machinome.occt`
or the provider), raising `No module named 'OCP'` where the user needs `pip
install "machinome[occt]"`. With the engine's own `require_extra` (Decision 4),
`_absent` also accepts an `ExtraUnavailable` whose `extra` is `occt`:
`exact_engine()` answers `None` and `require_exact_engine` raises
`ExactEngineUnavailable` naming the install line, unchanged in wording. An OCP
found and failing still propagates. The seam names no kernel; it already spells
`occt` in its message.

### 7. The command table names the module a command needs

`COMMANDS` values become `(module, class_name, needs)`; `needs` is `None` for
every command but `'import-step': ('machinome.manager.import_step',
'ImportStep', 'machinome.node.step')`. In `manage()`, once `selected` is known
and before `resolve_command(selected)`, a `needs` module is imported; on
`ExtraUnavailable` the CLI writes `Error: machinome <command> needs the
<extra> extra: <refusal>` to standard error and exits 1. Any other import
error propagates, as `resolve_command`'s docstring requires of a broken
install. The help path (`machinome -h`, no command) resolves classes as today
and imports no `needs` module, so it lists `import-step` with or without the
extra and costs what it costs now; `machinome import-step -h` is a selected
command and refuses.

`manager/import_step.py` imports `StepAssembly` from `machinome.node.step`
inside `handle()` (still lazily, for `-h`); `_load_step_assembly` and the
`ImportError` handler naming `pip install cadquery` are removed, since the
CLI answers absence before `handle()` and a broken install must report itself.
`test_import_step.py`'s `test_the_kernel_missing_is_a_checked_failure` becomes
a CLI-level subprocess test with the blocker (task 2.4).

Why this shape (the plan's D3: "a command table naming the module,
`machinome.node.step`, and the extra"): the table names the module; the extra
comes from the module's own refusal, so it is stated once, by the module that
needs it. The implementation stays in `manager/` for this layer; at the cut the
entry becomes the satellite's module and the CLI derives the extra of a
missing satellite by rule 2.

Rejected: (A') import `machinome.node.step` at the top of
`manager/import_step.py` and catch the refusal from `resolve_command` (the
help path would then import cadquery and OCP, about 1.5 s, and need its own
refusal handling to list the command); an extra column in the table (a second
copy of what the module declares); an entry-point group (D2).

No contract version for this seam in this layer: the CLI resolves no
implementation from `machinome.node.step`, only its presence, so there is no
provider contract to check. ADR-162 said `import-step` "will follow" its
pattern; it does when the command's implementation moves into the satellite.

### 8. The markings reducer behind a seam

- `machinome/node/build123d.py` gains `SVG_REDUCER_CONTRACT = 1` (a literal),
  `svg_regions(path)` (the body of today's `Svg.regions()`, logging and
  refusals unchanged) and `svg_triangles(path, tolerance)` (today's

- `machinome/node/markings.py` declares `SVG_REDUCER_CONTRACT = 1` and

- The recipe `marking-svg-v1:<tolerance>` is unchanged: same algorithm, same

### 9. The two path-extension lines

Both `machinome/__init__.py` and `machinome/node/__init__.py` extend their
`__path__`, the plan's verified mechanism, with one correction: only
directories without an `__init__.py` of their own are admitted.

```python
def _portions(path, name):
    import os, pkgutil
    found = pkgutil.extend_path(list(path), name)
    return [*path, *(p for p in found[len(path):]
                     if not os.path.isfile(os.path.join(p, '__init__.py')))]
__path__ = _portions(__path__, __name__)
```

(defined once in `machinome/__init__.py` as `_namespace_portions`, imported by
the node root).

**Finding, probed 3 October 2026.** The workspace venv installs the primary
checkout in compat editable mode (`__editable__.machinome-0.7.0.pth` puts
`/home/asa/devel/machinome/machinome` on `sys.path`), and every bench runs with
`PYTHONPATH=<bench>`. The plain line `__path__ =
__import__('pkgutil').extend_path(__path__, __name__)` then appends the
primary's `machinome/` to the bench's `machinome.__path__`, and the primary's
`machinome/node/` to the node package's: in the bench, `import
machinome.exact` (deleted by `exact-engine`) resolved to
`/home/asa/devel/machinome/machinome/machinome/exact.py`. Every bench test, the
universe sweep and every validator would silently mix two checkouts wherever
the bench lacks a module the primary has, exactly the case a cycle that moves
modules creates. The plan's sentence "A regular package always wins over
portions found earlier on sys.path, so order does not matter" holds for which
`__init__.py` runs, not for which submodules resolve. A satellite never ships
`machinome/__init__.py` or `machinome/node/__init__.py` (the plan's check-dist
collision guard), so admitting only directories without one keeps every
satellite combination of the plan's matrix and excludes any second copy of the
core. With the filter, the probe's extended paths are the bench's alone.

**Cost.** `import pkgutil` 3.6 ms (it pulls `typing`, `contextlib`,
`weakref`, `collections.abc`), the scan about 1 ms, once per process each.
**Nothing uses them yet**: no satellite exists, and every module under
`machinome` and `machinome.node` is found in the core's own directory.
Rejected: deferring the lines to the cut (the charter orders them in this
cycle); the plain line (the finding).

### 10. vet follows

`vet/universe.toml` names no adapter path: `machinome` is a contract member
whole, so `machinome.node.<x>` passes as a contract member with no change, and

## SOLID review

**Single responsibility.** `machinome.extras` answers one question, whether a
module's kernels are installed, and words one refusal. Each kernel module
states its own needs. The CLI table locates commands and what they need; it
does not know extras. `markings.py` declares and places; reduction is the
build123d module's. *Bend:* `machinome.node.build123d` now has three
responsibilities, two node types and the artwork reducer, accepted because the
ratified table puts the kernel's three users in one module so that one
distribution carries one kernel.

**Open/closed.** A new kernel module needs no core row: it calls
`require_extra` with its own extra and kernels and is found at
`machinome.node.<x>` by the import system and, at layer 2, by the filtered path
extension. The one accepted exception is the extras metadata in
`pyproject.toml` (pilot). *Bends:* the node root's `_EXPORTS` still lists
every core leaf until the root cleanup; the CLI table's `needs` column and the
markings seam each name one known module, the D2 compromise, one string each;
`ExactEngine`'s `_absent` spells its extra.

**Liskov substitution.** Every leaf behaves as before wherever its extra is
installed; `Build123dSheetNode`'s move into `Build123dNode`'s module changes
neither type nor base. `ExtraUnavailable` is a `ModuleNotFoundError`, so code
catching the import system's errors keeps working, and layer 2's absent
satellite raises the same class.

**Interface segregation.** A project that uses only OpenSCAD, solid2, JSCAD or
STL leaves installs and imports no kernel; one using CadQuery installs no
build123d or molejo. The reducer's interface is two functions and a version,
not the build123d node API.

**Dependency inversion.** The core depends on `machinome.extras` (the refusal
type) and on seams that name a module, never on a kernel: markings resolves its
reducer on first use, the CLI imports `needs` only for the selected command,
the engine seam recognises the refusal type rather than a kernel name, and the
AST test of task 2.6 holds that no core module outside the kernel modules
imports a kernel. *Bends:* `machinome.node.step` imports
`machinome.node.cadquery` for `workplane_shape` (the leaf-contract cycle's
deferred reach); `manager/import_step.py` imports `machinome.node.step` (its
implementation moves at the cut); the node root's `_EXPORTS` names kernel
modules as lazy targets until the root cleanup.
