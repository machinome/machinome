## Context

Line numbers are the base's (`f6119628`), in `machinome/viewer/web/widget/src/viewer.ts` unless a file is named.

A clocked input with a finite `range` gets a slider in its row (`buildClockedRow`, 4001-4117; the slider 4075-4094). The slider listens on `change` alone (4090) and calls the panel's `move`, which is `clockedRequest(id, { to }, true)` (1705-1707): land a running drawing, take the bank, make one request whose final pose is judged and not shown, write the outcome into `clockedOutcomes`, start the drawing, rebuild the whole panel (`rebuildClockedChrome`, 1651-1763), and render only if nothing is drawn (1406-1461). The drawing is advanced by the frame loop (`drawingFrame`, 1584) and writes the panel through one narrow writer, `ClockedChrome.follow` (4333-4338), whose row writer (4105-4115) writes the field unless it is focused and writes the thumb unconditionally. The machine's pose hook (1313-1339) either judges (`judging`) or updates the tree and draws (`drawPicture`).

What a drag does today, read from the source and measured by the opening evidence (`workflow/evidence/enigma-dragged-slider-2026-11-22.md`): the browser moves the thumb and fires `input` at every step, nothing listens, the machine and the model stand; at the release `change` makes one request to the thumb's value and the panel is rebuilt, so the slider the pointer held is replaced by a new one standing at the drawing's origin, and the thumb and the model travel there over the gesture's duration (`gestureSeconds`, `clockedControls.ts` 262; 0.2 s for `case_open`, which no `by=` instruction names).

Checked for this proposal, beyond the evidence:

- **The base in jsdom.** A scratch test (deleted) mounted the real viewer in jsdom with `draw-on-change.test.ts`'s counting renderer and a hand-written clocked document (a float input on a 0-2 range with a `floor` commit and a stop at 1.5, a whole-number input, an input whose `scale` is 2), and dispatched a drag's events on the real slider: seven positions made no request and moved nothing; the `change` made one request (`to: 1.9`, admitted to the stop at 1.5); the slider element was replaced and the new thumb stood at 0; nothing was rendered in the release's task. On the same document with a clock declared and playing, a slider pressed before a frame was replaced by the next frame: the clock's transport makes one request a frame through `clockedRequest`, which rebuilds the panel (`clockFrame`, 1605-1625). jsdom clamps a range input's value to its range, as browsers do, and implements `valueAsNumber`.
- **What browsers dispatch.** A scratch Playwright script (outside the repository) recorded every event on a plain `<input type=range>` (Decision 1's table). Chromium (the suite's headless Chromium) with the mouse and with touch through `Input.dispatchTouchEvent`; Firefox with the mouse. The Firefox this Playwright (1.63) expects (build 1543) is not installed; the one installed (build 1538) runs when its `executablePath` is given. The suite's tests use Chromium only.
- **How a drag's requests compose.** On the same hand-written machine, 2,000 random monotone rising splits and 2,000 falling ones (including cuts exactly on the commit's surfaces) each left the same bank as one request to the end; so did 300 monotone splits of the calculator fixture's `crank` (four digit commits with carries and a stop), cuts on whole teeth included. A hand that went 0.7, 1.3, 0.7, 1.3 fired the commit twice, one request to 1.3 once. A document whose commit allows at most three crossings a request refused one request of 0.55 and admitted the same travel in five steps. These are checks on the machine as it is, not a theorem; G1 keeps checking them.

Premises of the brief that the record does not bear out, stated so the review can weigh them: the tempo decision is ADR-073, not ADR-066 (it was numbered ADR-066 on its branch and renumbered at integration); a clocked row shows no pinned mark (only the posed panel colours a pinned readout, 3666-3670; `ClockedInputControl.pinned` is computed and not rendered); the clocked corpus is `src/clocked-corpus.json`, read by `src/clocked/clocked-corpus.test.ts`; the clock's transport does make one request posed at once a frame, as the brief says, but through the same door as a gesture, so it rebuilds the panel and draws three times a frame (recorded by `draw-a-press-from-its-first-frame` and `draw-only-when-the-picture-changes`); and the installed Firefox does not run under this Playwright without naming its executable.

## Goals / Non-Goals

**Goals:**

- While a pointer holds a clocked slider's thumb and moves it, the machine is asked for the positions the thumb reaches and the model, the row and the readouts show the machine's answer within the frame, the thumb staying under the pointer; the machine, the model and the panel agree at every moment a maker can see. First requirement.
- When the press ends, the machine stands where the last position put it and nothing further is drawn for that gesture, whatever ended the press. A drag's tempo is the hand's.
- Everything that is not a drag stays as ratified: a typed value, a nudge, an arrow key, Page Up and Down, Home and End, and a click on the track are each one request drawn over its duration (ADR-065, ADR-073); a pressed instruction is as it is.
- Smoothness: at most one request a frame, posed once and drawn once, with no panel rebuild. Second requirement.
- Shown by tests red on the base, mutations for every rule, a generated-sequence proof and the browser's own pointer, with no wall clock and no project export.

**Non-Goals:**

- What a frame costs while something moves; the posed and the running panels; dragging a part; new mount options or handle methods; the `on-demand` mode, which presents no clocked panel (Decision 8); anything that lowers a part's resolution or sampling; molejo; any project's source.
- The field's lost focus after a typed value (`workflow/warts.md`, "A value committed with the field still focused loses the field") and the same loss after an arrow key (Found while proposing): a typed value and a key stay as ratified, and their rebuild is their own change.
- Viewer API (stays 30) and document versions (stay 1 to 14): verified in `widget/package.json` (`machinomeViewerApi: 30`, `machinomeDocumentVersions: [1, …, 14]`).

## Decisions

### 1. Which gesture is a drag (attack point 1)

**What the HTML standard says.** For a control whose interface has both interactive manipulation and an explicit commit (a range control moved by a pointing device is the standard's own example), the user agent queues an `input` event whenever the user changes the value and a `change` event when the user commits it: while the knob is dragged `input` fires at every change of position and `change` when it is let go. A value set by script fires neither. Keyboard changes are committed as they are made.

**What the browsers this suite can run dispatch**, recorded on a plain range input, in order (`pointermove`s of the window and `mousemove`s omitted except where they matter):

| Gesture | Chromium (mouse) | Chromium (touch, CDP) | Firefox 1538 (mouse) |
|---|---|---|---|
| pressed on the thumb, moved, let go | `pointerdown`, `mousedown`, `focus`, `gotpointercapture`, then per step `pointermove`, `input`; at the release `pointerup`, `mouseup`, `change`, `lostpointercapture`, `click` | `pointerdown`, `touchstart`, `gotpointercapture`, per step `pointermove`, `touchmove`, `input`; `pointerup`, `lostpointercapture`, `touchend`, `change` | as Chromium's mouse, without the capture events |
| pressed on the thumb, not moved, let go | `pointerdown` … `pointerup`, no `input`, no `change` | — | the same |
| pressed on the track away from the thumb, let go | `pointerdown`, `mousedown`, **`input`** (the thumb moved to the press point, before any `pointermove`), `pointerup`, `mouseup`, `change` | `pointerdown`, `touchstart`, **`input`**, …, `change` | the same as Chromium's mouse |
| pressed on the track, moved while held | as above, then per step `pointermove`, `input` | the same | the same |
| pressed, dragged off the element, let go outside | every `pointermove`, `input` and the `pointerup` still target the slider | — | the same |
| arrow keys, Page Up and Down, Home and End | per key `keydown`, `input`, `change` | — | the same |
| a held arrow key | per repeat `keydown`, `input`, `change` | — | the same |
| the wheel over a focused slider | `wheel` only; the value does not change | — | the same |
| a value set by script | nothing | — | nothing |

**The rule.** A **press** begins with a `pointerdown` of the primary button (`button === 0`; every touch and pen contact reports 0) on a slider of the current clocked panel while the clock's transport is not playing (Decision 5), and records the pointer's id. While the press is held, each `input` the slider fires is a **position**, read as `slider.valueAsNumber` in design units. A position is **drawn** when it is the first of its press and either no `pointermove` of the press's pointer has been seen since the `pointerdown`, or the input as the model shows it stood outside the slider's range at the press (Decision 7). Every other position is **followed** (Decision 3). An `input` outside a press is ignored, as today. A `change` of a slider is ignored while that slider's press exists or if the slider's press was released since the last animation frame and no `keydown` has reached the slider since (the release's own `change`, which every recorded browser fires in the release's task); every other `change` is today's one drawn request. The press ends as Decision 5 states.

**What the rule reads, and what it depends on.** Only the order of the events and the press's own pointer id; never where the browser paints the thumb. It depends on a browser reporting a track press's change of value before it reports any movement of the press's pointer. The standard queues both from one task source in the order they happen, and Chromium (mouse and touch) and Firefox did so in every recording. A browser that moved the thumb to a track press only on the first movement would have that first position followed, which is a jump: B4 holds the order in Chromium, and Firefox is recorded here only. A browser that recentres the thumb under a press on the thumb itself would report a small first position before any movement, which is drawn and then waited for; harmless.

**Each gesture, under the rule:**

- Thumb pressed and moved: every position followed; the release's `change` ignored.
- Thumb pressed, not moved: no position; nothing is asked; the press ends at the release.
- Track pressed and let go (a click): one position before any movement, drawn, at the press rather than at the release as today; the release's `change` ignored. A click is one request drawn from where the input stood, as ratified; it starts when the button goes down.
- Track pressed and moved: the first position drawn; the positions after it wait for that drawing and are followed once it lands (Decision 3). No frame shows the jump made at once.
- Touch: the same as the mouse, by the same events.
- Keys, a held key: no press; each `change` is one drawn request, landing the previous drawing, as today.
- The wheel: nothing changes, in either browser.
- Script: setting the value does nothing, as today; a dispatched `input` does nothing; a dispatched `change` is one drawn request, as today, unless it comes in the task of a release.

### 2. The element the pointer holds (attack point 2)

**Nothing replaces the panel while a press exists.** `rebuildClockedChrome` ends a press before it rebuilds (Decision 5), so a rebuild can never replace a held slider; every door that would rebuild ends the press first. No request of a press rebuilds the panel: each writes what it changed through narrow writers on `ClockedChrome`, which the panel's drawing machinery already has the shape of:

- `follow(following)`, as today (4333): for every moved input its field and its thumb, for every moved state or the clock its readout. The row writer does not write the thumb of the slider a press holds (`hold`, below); it writes the field as before, unless the field is focused.
- `report(id, outcome)`, new: writes the row's outcome line with `formatClockedOutcome(outcome)`, only when the text differs from the line's.
- `hold(id | null)`, new: names the row whose thumb no writer touches. Set at the press; cleared when the press is over (Decision 5), after which the thumb is written once, from the bank as the model shows it (the drawing's bank while one runs, the machine's otherwise), pinned at an end where that is outside the range.

What a commit can move: a committing relation writes only states (`clocked/document.ts` refuses a target that is not one), so a request moves its own input and some states; no other row changes, and the clock moves only by its own transport. The instruction buttons' outcomes are keyed by name and no request of a drag writes them. A pinned mark: the clocked row has none.

`clockedOutcomes[id]` is set at every request of a press, so a later rebuild shows what the row last said.

**What waits for the end of the press:** only the thumb, which is written once when the press is over.

**Focus.** Pressing a slider focuses it (Chromium and Firefox, `focus` after `mousedown`). Since the panel is not rebuilt at the release, the slider keeps the focus, the panel keeps its scroll position, and an arrow key after the drag acts on that slider. The field finding is not repaired by this change and is not made worse: a typed value still rebuilds.

### 3. What the machine is asked, and how often (attack point 3)

**One request a frame, for the latest position.** A followed position is stored as the press's `pending` position (design units) and nothing else happens in the `input`'s task. In each animation frame, after the clock's frame and the drawing's frame (2153, 2158), the press's step runs: if a position is pending and differs from the last one asked in this press, it lands a running drawing that is not the press's own (ADR-064: a gesture lands a drawing), makes **one** request `move(id, { to: pending })` through the machine's pose hook in a third mode that updates the tree and does not draw, writes the panel narrowly (Decision 2) and records the position as asked. If the press's own drawn jump is still running, the step waits.

**Nothing queues.** There is one pending value, overwritten by each later position. A request that costs more than a frame (58 ms measured for a pose on the Enigma's `operation.press`; the Curta's 40 ms in September) makes that frame long; the browser delivers whatever positions came meanwhile (Chromium coalesces pointer moves while the page is busy), and the next frame asks once, for the latest. The machine is never asked for a position that a later one has replaced before its frame.

**The last position is never dropped.** Whenever a press ends (Decision 5) a pending position not yet asked is asked at once, in the task that ends it, unless the machine it would reach is gone. **Never asked twice in succession:** a pending position equal to the last asked is discarded. The same value reached again after another is asked again, because the bank it starts from differs.

**Made in the frame, not in the event's task**, so that several `input`s in one frame cost one request, a request cannot run in a task that the frame then repeats, and the loop's one draw shows it (Decision 6). Chromium dispatches a pointer's movement before the frame's callbacks (in the recordings each `input` of a drag came before the next frame's callback), so the position it produces is asked and drawn in the same frame. A drawn jump (Decision 1) is made in the `input`'s task, as every drawn gesture is made in its own, by the press itself: through `clockedRequest`'s drawn path (land a running drawing, one judged request, the tempo, `startDrawing`) without the `endPress` that path calls for other gestures, and with its rebuild replaced by `report`; it renders only where no drawing starts, as any drawn gesture does.

**The `on-demand` mode** has no frame and presents no clocked panel (requirement "An on-demand viewer poses and draws a clocked machine": "no clocked panel"; `options.ts` requires `driverControls: 'none'`), so it has no slider and no press.

**The bank a drag leaves, compared with one request to the same value.** A drag is the sequence of requests it made, each atomic, each from the bank the one before it left. The bank it leaves is that sequence's, which is what the generated proof checks against a fresh machine replaying the log.

- A travel in one direction, with commits along the way: the same bank as one request to the last position. Every commit fires on a rising crossing of its level located on the path; splitting the path at a position moves no crossing, and a split exactly on a surface gives the crossing to the piece whose path contains its landing (ADR-128, closure 1, as `clocked/events.ts` mirrors it). Checked on 4,300 random splits (Context). This holds while nothing clips differently (next items).
- A hand that goes back and forth across a commit's level: the commit fires at each rising crossing, so a hand that goes 0.7, 1.3, 0.7, 1.3 across a `floor` level at 1 commits twice where one request to 1.3 commits once. That is what the hand did: the machine was moved across the level twice.
- Whole-number inputs: the slider's step is 1, so every position is a whole number of design units and every request lands on one; the first bullet holds.
- A travel the machine would refuse whole: one request is atomic and a drag is not. A request that crosses more surfaces of one relation than the document's limit allows is refused whole, while the same travel in shorter requests is admitted; a commit that moves a coordinate out of range refuses the whole request (its message says "Split the request at that event"), while a drag stops or passes there piece by piece. And the clip reads each bound over the bank its request starts from, so a stop whose bound reads a state that a commit along the way wrote can hold one drag where one request is refused, or the other way round. In each case the bank is what the hand's requests made, each admitted by the machine as it stood. They differ from one request; that is what the hand did.

### 4. Short answers and refusals (attack point 4)

**While the thumb is held.** A followed position the machine admits short (a stop) leaves the model, the field and the readouts at the stop, while the thumb stays under the pointer beyond it. A position refused leaves the bank, the model and the panel where the last admitted position put them. The outcome line reports **the drag as a whole**: for a completed latest request, `completed` with the travel admitted since the press, `(bank[id] − start) × scale` in design units (one subtraction, the formula a single request's `admitted` uses, so a drag that ends where one request would reads the same number), and the stops of the latest request; for a refused latest request, `refused` with its message. Later positions that repeat a stop or a refusal produce the same text, and `report` writes nothing when the text is the line's already; no request of a press rebuilds the panel, so nothing flickers. A thumb held still beyond a stop asks nothing (Decision 3).

**At the end of the press** the thumb is written to where the machine stands, as the rebuilt panel would place it (`sliderPlan`, `clockedControls.ts` 298): a stopped or refused drag's thumb goes back to the stop or to the last admitted position; a position outside the range pins it at an end while the field stays truthful. The outcome line keeps the drag's report, which a later rebuild repeats from `clockedOutcomes`. Every other gesture still reports its one request.

### 5. Other authorities over the pose, and how a press ends (attack point 5)

**What ends a press, with its last position asked** (`endPress`): the release of its pointer (`pointerup` listened on the window in the capture phase, so a release anywhere is seen; Firefox fires no capture events and targets the slider anyway, Chromium captures); `pointercancel` of its pointer; `lostpointercapture` on the slider; a `keydown` on the held slider; a `pointerdown` on another clocked slider (which then starts its own press); and every door below. No `change` is needed: the release's `change`, when it comes, is ignored (Decision 1). A second pointer on a held slider is ignored, and its release ends nothing. The listeners a press needs outside its slider (the window's, for its pointer's movement, release and cancellation) are added when the press begins and removed when it ends or is dropped: a viewer no pointer holds a slider of has added nothing to the window, so a pointer moving over a still page runs no code of this change.

**What does not end a press.** The window losing focus and the page being hidden end nothing. While the button stays down the browser goes on reporting the thumb's positions, and a press ended there would leave them unfollowed and hand the release's `change` to the drawn path, which is the finding again. A release the browser never reports leaves a press whose every position has been asked or is asked by the next frame; the next press, key or door ends it. Nothing in that state is wrong: the machine stands where the thumb was last put.

**When the press's own drawn jump is still running at the release**, the drawing continues and the latest position, if any, is asked in the frame the drawing lands; then the press is over. A click on the track, released before its drawing lands, therefore draws in full as ratified. A door, a key or another press during that interval lands the drawing and asks the position at once.

**Doors.** Every function that makes a request, reposes the machine or rebuilds the clocked panel calls `endPress` before it acts: `clockedRequest` (the field's commit, the nudge pair, a slider's `change`, the clock's frame and step), `clockedPlay` (the instruction button and `machine().trigger`), the panel's reset, play, step and its step amount and speed, `focusOn` (the breadcrumb and `setRoot`), `refreshControls` (a reload and an in-place update), the handle's `move`, `restore`, `reset` and `setClockPlaying`, and `rebuildClockedChrome` itself, so that a door added later cannot replace a held slider. The drag's last position is therefore asked before the door's own request, and the door's request acts on the bank the hand left.

- **A drawing running when the press begins** keeps running; the press does not land it. If it moves the pressed input, its frames write the field and not the held thumb. The press's first position lands it, as every gesture does, and then acts.
- **An instruction pressed, a value typed, a nudge, a host's `machine().move`, `restore`, `reset` or `trigger`** while the thumb is held: a door; the press ends, its position asked, and the thing acts. Its rebuild replaces the slider; the old one is detached and its events ask nothing (a row's listeners act only while their slider is connected). The pointer the maker still holds moves nothing until it is pressed again.
- **A playing clock.** While the clock's transport plays, where the machine declares a clock, no press begins: a `pointerdown` on a slider starts nothing, its `input`s are ignored and its `change` is today's one drawn request. The base's transport rebuilds the panel on every frame it plays, so a slider cannot be held there today either, and no project or fixture carries a clock beside a ranged input; this change leaves that case as it is and records it (`workflow/warts.md`). So no frame of a press makes two requests. `machine().setClockPlaying(true)` and the panel's play button during a press are doors: the press ends first, then the clock plays.
- **A republish, a reload, an in-place update.** While the new document loads the press goes on, on the machine that is mounted. When `startMachine` replaces the machine (1295, called at 1783 and 2304) the press is dropped with nothing asked and its slider's events ask nothing until the panel is rebuilt: no request reaches a machine that is gone or a machine the maker did not drag. When an in-place update keeps the machine (same identity, 2275-2276, 2303), its `refreshControls` is a door and the last position is asked of that same machine.
- **`dispose()`**: the press is dropped, nothing asked; the window and document listeners are removed with the loop's.
- **A lost capture or a cancelled pointer**: each ends the press with its position asked; the state is the one a release leaves. **A window that loses focus or a hidden page** ends nothing (above). The design never needs a `change`: every position is asked by its frame or by whatever ends the press.

### 6. The frame loop (attack point 6)

- **Drawn once, in the frame.** A followed request poses through the hook's new mode, which calls `tree.update` and not `drawPicture`. The update raises the picture revision (ADR-080) where its change set reaches a node, and the loop's own decision at the end of the frame (`changed()`, 2104) draws once. A request in a door or at a release is drawn by the door's own draw or by the next frame's, once.
- **A thumb held still costs nothing.** No `input`, no pending position, no request, no update, no draw: the frame is ADR-080's still frame.
- **A held press is not "moving".** `moving()` (2098) is not given a term for it: a press changes the picture only through its requests, each of which raises the revision, so a frame in which nothing was asked has nothing new to draw. A term would draw every frame of a thumb held still, which ADR-080 and this change's goal forbid. The press's drawn jump is a drawing and counts as moving while it runs, as today.
- **The last position is on screen when the pointer lets go.** A position asked in a frame before the release is already drawn; one asked by the release is drawn in the next frame.

### 7. Whole numbers, scales and pinned thumbs (attack point 7)

- **A whole-number input** (`dtype: 'int'`, slider step 1): positions are whole design numbers and each request lands on a whole native value (`native`, `clocked/machine.ts` 138), so the model, the field and the bank are whole at every frame. A followed request is posed, not drawn, so the drawing's truncation (`clocked/drawing.ts` 111) does not apply to it.
- **A `scale` other than 1:** positions are design units, as the slider's plan is (`sliderPlan` reads `displayValue`); `move(id, { to })` speaks design units and converts once to native; the field and the thumb are written from the bank through `displayValue`. The outcome's travel is `(bank − start) × scale`. Pending and asked positions are compared in design units.
- **An input outside its range when the press begins:** its thumb is pinned at an end. The first position after a movement is a jump the hand did not make (from where the input stands to near the end), so it is drawn, and the positions after it wait for that drawing, exactly as for a track press. "Outside" is read from the bank as the model shows it at the press (the drawing's while one runs), through `clockedInputControl(...).pinned` (`clockedControls.ts` 316-339), not from the thumb.
- **An input with no range** has no slider (`sliderPlan` returns null) and nothing here applies to it.

### 8. What must not change (attack point 8)

- **The posed panel** (`buildDriverRow`, 3572 onwards; its slider writes on `input` and `change`, 3684-3685) and **the running panel** (`buildRunChrome`, 4346 onwards): untouched; the new code is in `buildClockedRow`, `buildClockedChrome` and the clocked parts of the mount.
- **The part controls** (`partSurface`, `rebuildPartControls` 976): untouched; they drive a run, never a clocked machine.
- **The mount handle:** no method is added and none changes its meaning. `machine().move`, `restore`, `reset`, `trigger` and `setClockPlaying` keep their requests and answers; each ends a press first, which on the base no press could need. Two things a host can observe change, both the substance of the feature: `machine().state()` read during a drag follows the thumb, and a host's call during a drag acts after the drag's last position.
- **The viewer API and the document versions:** 30 and 1 to 14, verified. Nothing a host can require or detect through the API is added; ADR-065 and ADR-073 changed the panel's on-screen behaviour without a bump for the same reason.
- **The `on-demand` mode:** unchanged. The finding cannot hold there: it presents no clocked panel and so no slider; a host poses by request (ADR-077). O1 holds it.
- **Drawn gestures:** a typed value, a nudge, a key and a slider's `change` outside a press go through `clockedRequest` exactly as today, rebuild included.

### 9. The requirement's words (attack point 9)

The delta restates two requirements of `viewer-package` in full, every scenario kept.

"A maker operates a clocked machine on screen":

- "every such gesture SHALL submit exactly ONE request to move that input TO the value the gesture names" becomes every gesture other than a drag, and a drag is defined: what a press and a position are, which position is drawn and which followed, at most one request a frame for the latest, none twice in succession, the last never left unasked, nothing for a thumb held still, the end of a press by whatever ends it, the thumb placed where the machine stands, the panel not replaced and the focus kept, the outcome of the drag as a whole, the bank of a drag being the bank of its requests, no press while the clock's transport plays, and what ends a drag first.
- "A gesture on a HANDLE SHALL be ONE request, and the transition that request reports SHALL BE DRAWN" gains "other than a drag's followed position".
- "A handle SHALL stay usable while a drawing runs; a gesture on one LANDS the running drawing" gains: except the positions after a press's own drawn jump, which wait for it.
- "A control a maker is EDITING SHALL NOT be rewritten by a drawing that is running" gains that a slider a pointer holds is such a control; the base's row writer wrote it (Found while proposing).
- The scenario "A slider's commit is drawn" keeps its name and now names a click on the track and the keyboard; the drag is in new scenarios.

"The viewer plays a clocked instruction as one drawn transition": the sentence that draws "the transition a maker's GESTURE on a handle produces" excepts a dragged slider's followed positions, which are posed at once like a request on the mount handle; the scenario "A handle's gesture is drawn like an instruction's press" excepts them in its WHEN.

Read and unchanged: "A maker runs an elapsed clocked machine on screen" (no press begins while its transport plays, so its panel is as it was); "An on-demand viewer poses and draws a clocked machine" (no panel); "A continuous viewer draws a frame only when its picture has changed" (a followed position is a change shown no later than the next frame, and a held press is not among the motions drawn in doubt); "On-screen machine controls leave the machine visible" ("compacting the panel SHALL NOT ... change the request it makes": the panel's layout is untouched); the part gestures of "A maker drives a running machine by touching its parts" (2582-2620), which speak of a running machine's parts; the posed panel's "dragging the slider" sentences (886-946), which this change does not touch.

### 10. Cost (attack point 10)

What a followed position costs, in terms of what the code does today:

- one `machine.move`: the clip over every bound's level, the events of the commits naming the input, the judgement of the final bank, the pose hook's existing copy of the bank (`machine.state()`, 1321) and its diff of the ids that moved;
- one `tree.update` over the ids that moved, flexible parts the change reaches included (the same pose a drawing's frame makes);
- the narrow writes: `clockedFollowing` over the moved ids, one field and thumb write per moved input, one readout write per moved state, one text comparison for the outcome line and a write only if it differs;
- one draw, by the loop.

Not done for a followed position, where the base's request does it: the bank copy taken before a drawn request (1417), the panel's rebuild (`clockedControlLayer` and every row's DOM), the hook's own draw and `clockedRequest`'s second draw. Nothing per position grows with the panel. The hook's bank copy is the base's, and kept.

## For the pilot

- **This revises ADR-065 and restores nothing.** The clocked slider has listened on `change` alone since it was written; ADR-065 set a request per pointer sample aside by analogy with the instruction sliced into frames that ADR-064 records the pilot rejecting, and no record shows the pilot being asked about a drag. ADR-064's own reason, that slicing "puts the machine back in the frame loop", applies to a drag in the letter: a drag asks the machine once a frame while the hand moves. The difference this design rests on is that a drag's positions are the hand's, not a declared stroke's.
- **A press on the track is drawn from the press**, not from the release as today: a press held on the track shows the model travelling while the button is still down.
- **After a drawn jump** (a track press, a pinned thumb), **the positions wait for its drawing**, up to the gesture's duration (0.2 s, or a declared tempo's share of a travel, which on the Curta's crank is 2 s a turn); the model then joins the thumb in one frame. Landing the jump at the first movement instead would show the jump's remainder in one frame.
- **The outcome line reports the drag as a whole**: the travel admitted since the press, with the stops or the refusal of its latest position.
- **The bank of a drag is the bank of its requests**: equal to one request for a travel in one direction; a commit crossed back and forth fires each time; a travel one request would refuse whole can be admitted step by step, and a stop that reads a state can hold differently.
- **Host-visible:** `machine().state()` follows the thumb during a drag, and a host's call during a drag acts after the drag's last position.

## Alternatives rejected

- **Listening on `input` and making each position a drawn gesture** through `clockedRequest`: every position drawn over 0.2 s and landed by the next one, so the model lags and then jumps; and each request rebuilds the panel, which replaces the slider the pointer holds.
- **The brief's measured mechanism, `machine().move` each frame:** it rebuilds the panel at every call (2397), replacing the held slider, and draws in the call. Its cost is an upper bound on Decision 10's.
- **One request per `input` in the event's task:** several requests a frame where a browser does not coalesce, requests that queue behind a slow one, and a pose the frame might draw twice.
- **Telling a jump by where the thumb is painted**, or by the size of the first change: the first depends on the browser's thumb and the page's styles; the second confuses a fast hand with a slow track press.
- **Landing a press's own drawn jump at its first movement:** a track press followed at once by a movement shows the rest of the jump in one frame, ADR-065's defect.
- **Chasing the thumb with drawn segments:** the model would trail the pointer for the whole drag and never follow within the frame.
- **Rebuilding the panel at the release:** the slider loses the focus and the scroll position, the field finding's cause.
- **Stopping the clock's transport at a press, or writing the transport narrowly so that a drag goes on while it plays:** either makes a slider draggable beside a playing clock, which it is not today. No project or fixture carries a clock beside a ranged input, so neither is built; struck in review and recorded as a finding.
- **Ending a press when the window loses focus or the page is hidden:** struck in review (Decision 5, "What does not end a press").
- **A term for a held press in `moving()`:** a thumb held still would draw every frame.
- **A new handle method or mount option:** a correct design needs none.

## Risks / Trade-offs

- [A browser that reports a track press's jump only after a movement] → the jump would be followed; B4 pins the order in Chromium; Firefox recorded here, not in the suite.
- [A door added later that rebuilds the panel without ending a press] → `rebuildClockedChrome` ends it itself; MU14 shows which calls are load-bearing.
- [A request costing more than a frame] → one pending position and one request a frame; the drag's frames are as long as its requests (Decision 10's predictions).
- [The bank of a drag differing from one request's] → stated, tested (R11, R12, G1) and for the pilot.
- [jsdom does not implement a range input's drag] → the synthetic events prove the rule given an order of events; B1 to B5 hold the order and the result in Chromium.
- [Admitted time] → none claimed beyond the reviewer's measurement.

## Corrected in review, before the planning commit

The reviewing agent changed three things in these artifacts; the proposer's text is otherwise as written.

- **No rule for a playing clock.** The proposal stopped the clock's transport at a press and wrote its button narrowly (a writer `transport`, a test, a paragraph of the requirement and a decision for the pilot). - **A window that loses focus and a hidden page end nothing.** The proposal ended the press there, answering the brief's own question about a release that never comes. - **Nothing on the window while no slider is held.** The tasks installed the window's listeners with the loop; they are added at the press and removed at its end, so a still page runs none of this change's code when a pointer moves.
