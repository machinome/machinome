## Why

The viewer evaluates a document's shared, hash-consed expression graph by a recursive, memoized walk (`valueOf`, `compute`, `resolveName`; ADR-043, ADR-044). On the Enigma I page (`enigma-i` at `081f4e6`, measured script only on viewer `e87683e3`), any operation input that moves feeds about 507,000 of the document's 546,768 nodes, so every pose computes about 540,000 node values, about 100 ms of script, about half of a key press frame. A scratch prototype compiled the graph reached from the binding table into a flat program over typed arrays, ran it in one loop before a pose and let `valueOf` read the result: a run cost about 4 ms, a key press frame went from 187 to 111 ms and showed 19 pictures in its two seconds instead of 11, and 30.6 million values compared with the walk's showed no mismatch (`workflow/warts.md`, "A moved input recomputes the whole formula graph, node by node"; `workflow/evidence/enigma-formula-evaluation-2026-11-20.md` and the patch beside it). Read against the source, the prototype also has defects the Enigma does not reach: it hands a comparison's result out as 1 or 0 where the walk gives `true` or `false`, a declined run leaves stale values for the next pass, a call of `random` is frozen after its first value, a driver named like a function is checked only against the compile scope, and two documents operated alternately recompile at every switch.

## What Changes

- A pose (`WidgetTree.update` and `WidgetTree.admit`) of a document whose binding table holds at least a source-defined minimum of entries first runs that table's **flat program**: the part of the graph reached from the table's roots that the program covers, compiled once per table and store generation, in dependency order over typed arrays. `valueOf` then answers a covered node from the program for that pass, and the recursive walk computes everything else exactly as today.
- The program covers a node only when its value is provably the walk's: a numeric literal; `$t`; a binding name (sharing its root's value); a name read from the scope that holds a number; unary `-`; `+ - * / %`; `< <= > >= == !=`; and a call of one of twenty named functions of the expression language that are total and pure over numbers; and only when every child is covered. A comparison's result stays a boolean wherever it leaves the program. Everything else, and everything above it, stays with the walk: `&&`, `||`, a ternary, `===`, `!==`, bitwise operators, a member or index read, arrays, objects, non-numeric literals, `profileOverlap`, `random`, any other function, a function or an owner map used as a value.
- The flat pass cannot throw. What can throw in the walk is either outside the program or is detected by the program's checks, which then leave the whole pass to the walk; the walk throws it where it throws today, with the same message. A scope the program cannot serve (an input missing or not a number, a driver named like a called function) is left to the walk for that pass and changes nothing in the program.
- A pose computes only what its moved inputs feed: the program is ordered into segments by the set of inputs each entry depends on, a pose runs only the segments a changed input belongs to, and an input set of any size is held without saturating.
- Lifetime follows the store: one program per binding table, retained while the table and the store generation live, dropped at every store reset (the three reclamation points, settlement and the last viewer's disposal all reach it) and never invalidated by a node interned later. Two documents operated alternately keep one program each.
- The clocked machine's solving and bounds, a running program's ticks and `evaluateExpression`, `PathValue` and `ExpressionPath`, validation and part controls do not run the program; their cost changes by one integer comparison per memo miss.
- `expressionMetrics().resolutions` keeps its meaning, values computed by the recursive walk; the widget's source adds `flatPassMetrics()`, a source-only `FLAT_PASS` (the minimum and a self-check that compares every covered value with the walk's), and a probe for its own tests. None of it is on the mount handle.
- New tests: red-first counts of the work a pose does and one test per exactness edge, in `src/flat-pass.test.ts` and `src/tree.test.ts`; a parity proof over every committed fixture and corpus with a table, in `src/flat-pass-parity.test.ts`; deliberate mutations of the implementation showing the edge tests catch the prototype's defects.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `viewer-package`: "A repeated subexpression is evaluated once per pass" states that a pose of a document with a large enough table computes its covered formulas in one flat pass, only where an input moved, and that the walk's resolutions and the flat pass's values are counted apart; "A named binding is resolved where it is used" allows that pass to compute an entry nothing in the pose reads, only when an input of that entry moved, and never visibly. A new requirement, "A pose evaluates a large document's formulas in one flat pass", states exactness, refusals, the scopes it serves, the work it does and its lifetime. Every existing scenario of both modified requirements is restated, two with a changed outcome.

Review, 20 November 2026. The repository agent reviewed the proposal, the design and the delta against nine recorded attack points and against the source of `expressions.ts`, and approved proceeding to implementation without a revision. The design departs from the reviewer’s own prototype where the prototype was wrong beyond the one document it ran on: it handed a comparison out as a number and its self-check could not see that; a declined run had already written its inputs; it covered every function of the context, `random` included; and it recompiled whenever two documents alternated. The reviewer accepts what the design states as costs: a covered entry is computed whenever an input it reads moves, whether or not the pose reads it; the first pose of a large table pays its compilation; a graph too deep for the recursive walk may now pose. The first of these qualifies a ratified sentence, "An entry SHALL be evaluated only when something reads it", for poses served by the flat pass. The reviewer judges it inherent in the change the pilot ordered, not a separate choice, and reports it to the pilot in plain words with the result; integration into `main` remains the pilot’s, and with it the last word on that sentence. The design’s predictions are predictions; the reviewer’s measurement on the Enigma page decides.
