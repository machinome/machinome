## Why

On the Enigma I page (`enigma-i` at `081f4e6`, viewer at framework `56de33dd`, the default `continuous` render mode) an animation frame in which nothing changes costs 20 to 23 ms of script, 16 to 19 of it the draw and 3 to 4 a tree update whose change set names nothing, and asks the graphics card for 3,347 draw calls and 44.8 million triangles, on every frame for as long as the page is open; in the eight seconds after a key press 281 to 338 frames are drawn and 33 to 38 of them change anything. Skipping the draw and that update from outside the viewer took the frame to 0.1 ms (`workflow/evidence/enigma-idle-frame-cost-2026-11-21.md`; `workflow/warts.md`, "Every part has its own geometry and material, and an idle page draws all of it every frame"). The loop draws because it cannot tell whether anything changed; this change gives it a way to tell, with the picture on screen always being the current state as the first requirement and the saving as the second.

## What Changes

- In the `continuous` render mode the frame loop draws only when the picture can have changed since its last draw: the tree that is shown was replaced, something the viewer's owners of the scene count was written (a pose, a flexible part's buffers, visibility, an in-place update's application, a material a mesh points at), or the camera moved (compared by value each frame, whoever moved it). The loop still runs on every animation frame and still advances the ramps, polls the hover and runs the clock, the drawing of a request and the timeline as today; a frame in which nothing changed draws nothing.
- The loop's tree update whose change set names nothing (`time` false, no driver moved) is skipped; it writes nothing to the scene for any kind of document (design Decision 4).
- When in doubt the loop draws: on every frame, as today, while the timeline plays, a ramp moves, the clock plays, a request's transition is drawn, a run is started or a gesture on a part is engaged, and on the frame each of them ends. After the browser restores a lost graphics context and when a hidden page is shown again, the next frame is drawn.
- A resize draws at the new size inside the resize observer's callback, so the frame in which the canvas is resized (the first frame after a mount among them) no longer shows a cleared canvas. That frame looks different from today: it shows the picture where it showed a cleared canvas. (Corrected in implementation: in headless Chromium only a real change of size left its frame cleared, not the first frame after a mount; design, the note under Context.)
- Every call that draws before it returns today (sixteen places in `viewer.ts`) still draws, unconditionally, through one `draw()` that also records what it drew.
- The `on-demand` render mode does not change: no loop, no recorded draws, no listeners, the resize observer draws nothing.
- Tests red on the base by count, through a new jsdom bench that mounts the real viewer with a counting renderer and drives its loop frame by frame (the suite has never run the loop): draws and tree updates over still frames, and for every source of a changed picture a draw within one frame and none after it; a detector that reads everything a draw reads and fails when it differs from what was last drawn; per-frame counts during every motion recorded on the base and reproduced; generated sequences of host and maker actions; mutations per source. A browser test that changes each kind of thing once, waits, and compares the screenshot with one taken after a forced redraw; one that reads the canvas inside a resize; WebGL draw calls counted over still frames.
- **Host-visible:** a script that reads the canvas's drawing buffer (`toDataURL`, `drawImage`, `readPixels`, `captureStream`) in an animation-frame callback that runs after the viewer's, relying on the viewer having drawn in that frame, now reads a cleared buffer in frames in which nothing changed. Reading it in the task of a call that draws, a page screenshot and what a maker sees are unchanged. One test of this repository reads that way (`tests/test_regulator_document.py`) and is restated. Whether this is accepted is the pilot's decision (design, "For the pilot").

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `viewer-package`: one requirement is added, "A continuous viewer draws a frame only when its picture has changed". No ratified sentence of the baseline changes: none promises a draw on every frame, and every sentence that assumes one holds as written (design Decision 9 lists them).
