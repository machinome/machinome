## Context

The viewer's expression store (ADR-043) is one page-scoped, hash-consed table of nodes, with a string-to-root map, free-name sets and a pass memo beside it. It is a pure cache: emptying it costs a re-parse and never a wrong number, because every holder of node ids outside the store checks `expressionGeneration()` and rebuilds from source text when it moved (ADR-044's generation guard and ADR-043's lifetime amendment). Today `withExpressions` empties the store at the start of every *outermost* operation once it holds `EXPRESSION_LIMITS.nodes` (125,000) or more; a protected operation may exceed that while it runs; `releaseExpressions()` empties the store when the last mounted viewer is disposed, deferring to the end of an open scope.

The comment on `withExpressions` says the threshold "is headroom for obsolete work, not a limit on one live document's working set". The test it applies cannot tell the two apart: it counts every node in the store, live or obsolete, at the start of every operation. The Enigma I page (`enigma-i` at `081f4e6`) mounts a clocked document of 546,768 nodes, so every pose, press and drawn frame begins by discarding the graph it is about to need and preparing all 214,278 binding entries again (about 2.3 s per preparation on the measuring host; `workflow/evidence/enigma-press-script-cost-2026-11-20.md`). The same cause applies to the mounted Voron-2 (483,728 nodes), whose poses were not timed.

Where obsolete expression state comes from was established from the source for this design:

- **Document loads.** Every document the viewer shows enters through `loadDocument` → `assertRenderable`, whose two callers are `replaceTree` (initial mount and `reload()`) and `manifestChanged`; `artifactChanged` replaces geometry and rebuilds part controls from the document already loaded, without loading one. `assertRenderable` is one protected synchronous operation that prepares the whole document: its binding table, its running program or clocked machine, its operations, flexible parameters and colours (`mount-voron-export`). It is always outermost in the viewer: `loadDocument` calls it after awaiting the fetch and the JSON parse, and every scope is synchronous and closes in `finally`, so no scope is open when a continuation runs.
- **The replacement that follows a load.** A successful validation is not yet an installation. `replaceTree` then awaits the new tree's assets and `startRuntime` before it swaps trees; `manifestChanged` awaits `tree.reconcile` and `startRuntime`. Throughout that window the standing model keeps operating (animation frames, clocked requests, run frames), and the replacement can still be refused after validation: a required asset fails, `assertCaptureDocument` refuses the document for an on-demand mount, or the viewer is disposed. A replaced document's graph becomes obsolete when its successor is installed; a refused document's graph, partial or complete, is obsolete at once.
- **Disposal.** A disposed viewer's graph is obsolete whether or not other viewers remain; when it is the last viewer the store is emptied.
- **Nothing else.** Every `prepare` call site after load was traced to text the loaded document holds or to text composed from it once at load:
  - `evalExpr` from `tree.ts` (operation strings), `color.ts` (`color.when`) and `flexible.ts` (flexible parameters): document text, all first prepared by `freeVariables` when the tree is built.
  - `bindings.ts`'s `roots()`: the document's entries.
  - `partControls.ts`'s `affineCoordinate`: a document operation, when part controls are rebuilt at load, reload or an artifact change.
  - `ExpressionPath` (`run/jumps.ts`, `run/run.ts`): `jump.level`, `plan.skeleton`, `constraint.expression`, all document text; new path objects are made per piece, new text is not.
  - `retainedKinkLevels` and the program and clocked `nodeOf` closures: document text, plus one string per clocked bound composed in `readBound` at load (`(${chain} - ${declared})`, and `String(bound.bound)` for a numeric bound), stored in the loaded descriptor and evaluated thereafter by the same string.

  A proposal-time probe on this bench (since deleted, with the source untouched) loaded each of the 30 clocked-corpus machines and ran its script twice, and loaded each of the 28 running-corpus machines through `Engine.load` and advanced it through all its scripted ticks: no request, tick or second pass added a single node after load.

A running program does not run in the page's store. `RunRuntime` starts one Web Worker per runtime, whose module instance has its own store; the worker's session loads exactly one program and the worker is terminated when the runtime is disposed. Only when a page's policy forbids the blob worker does the session run in-thread, sharing the page's store, after `assertRenderable` has already prepared the same document text there.

The disposal of a viewer that is not the last and a refused load were found in review to need reclamation points of their own.

## Goals / Non-Goals

**Goals:**

- A mounted document's prepared expressions are reused across consecutive operations — poses, clocked requests, drawn frames, tree updates and run ticks — whatever the size of the document, with no generation change between them.
- At the start of every outermost operation that is not a document load, the store holds fewer than H nodes that no loaded document has prepared (Decision 2), so retention stays bounded by the graphs of the loaded documents plus finite headroom, never by the number of past publications, successful or refused, nor by past disposals; disposing of the last viewer still empties the store; a protected operation may still exceed any threshold while it runs.
- A successful load of a large document costs it no second preparation at its first operation.
- Evaluation, generation guards, scope rules, refusals and every numerical result are unchanged.
- The suite keeps a way to reclaim before every outermost operation, and every test that relies on it proves that it did.

**Non-Goals:**

- Raising, scaling or deriving the numeric threshold; per-document or per-mount accounting of graph sizes.
- Any change to parsing, interning, evaluation speed, the binding table, the press path, flexible-part refills or the drawing load (the other findings of the same warts section).
- Sparing one mounted viewer's graph when a different viewer loads a document or is disposed (a stated limit under Risks).
- A cross-browser memory budget or a claim about GPU frame time.

## Decisions

### 1. Reclaim where obsolete state is created, not between operations

`withExpressions` stops deciding reclamation by size at the start of an ordinary operation. Let H be `EXPRESSION_LIMITS.nodes` (unchanged at 125,000). Reclamation is requested at the five points where obsolete state is created, and each request is honoured at once when no scope is open, or at the end of the outermost open scope otherwise, through the route the final-disposal clear already takes (`disposalPending`). Several requests pending at one scope end produce at most one reset.

1. **The start of a document load.** A second entry beside `withExpressions`, `withDocumentLoad(action)` in `expressions.ts`, behaves identically — nestable, synchronous, releasing in `finally` — except that, when it is outermost, it first empties the store if the store holds H or more. `assertRenderable` is its only production caller: it replaces its present `withExpressions` wrapper. A load entered inside an open scope (the viewer never makes one; a test or a later caller might) does not reclaim at its start, because no reset happens inside a scope; points 2 and 3 cover it (Decision 2, case 8).
2. **A refused load.** When the action of a `withDocumentLoad` throws, the entry requests a reclamation at H: the outermost load's `finally` empties the store if the refused document's partial graph, with whatever the load carried, has reached H.
3. **The settlement of a replacement.** On success, `withDocumentLoad` records the store's generation and the number of nodes the load added (A). `assertRenderable` attaches to its `LoadedDocument` an idempotent `settlement` handle over that record, with two methods; the first call wins and later calls do nothing.
   - `abandoned()` requests a reclamation at H. The viewer calls it on every exit from `replaceTree` or `manifestChanged` that does not install the validated document: a throw after validation (a required asset, `assertCaptureDocument`, `startRuntime`), and a disposal during the load.
   - `installed()` requests a reclamation at H + A while the generation is the one recorded, and at H once it has moved. The viewer calls it at the first statement after the replacement's last await and disposal check: in `replaceTree` immediately before the trees are swapped, in `manifestChanged` immediately after `startRuntime` and its disposal check. In both, a `finally` calls `abandoned()`, which does nothing once `installed()` has been called.
4. **Any viewer's disposal.** `releaseExpressions()` requests a reclamation at H whether or not it releases the last mount.
5. **The last viewer's disposal.** As today, the store is emptied unconditionally when the mount count reaches zero, deferred to the end of an open scope and cancelled if a mount is retained before that scope ends.

The reclamation at a load's start is what lets a successful installation keep the incoming graph. Without it, the standing document's graph would still be resident at the installation, of the order of a whole document when the standing document is large, and the installation's check would have to empty the incoming graph with it. With it, what the installation finds besides the incoming graph is only what was carried below H and what operations prepared during the window.

`loadProgram`, `loadClocked`, `bindingTable` and `Engine.load` stay ordinary operations. In the viewer they run nested inside `assertRenderable`, where the entry is already open. In a worker the store holds one program for the worker's life and is discarded with the worker. In the in-thread fallback, a reclaiming session load would empty the page store immediately after `assertRenderable` prepared the same text there and cost one full rebuild for nothing; as an ordinary operation it reads that text from the string cache.

The threshold's meaning becomes what the comment already claims for it: headroom for obsolete work, not a limit on the working set of what is loaded.

Why the next larger model is not a fourth meeting: no number now stands between a loaded document and its own graph. The constant bounds only obsolete state. A larger document makes a larger store, bounded by that document's own expressions, and the first limit it meets is the page's memory, which its geometry dominates (1.9 GB on the Enigma page against tens to low hundreds of megabytes for the store; see Decision 4).

### 2. The invariant and what bounds retention

A document is **loaded** from the successful end of its validation until its own settlement is `abandoned()`, a successor in the same viewer is settled `installed()`, or its viewer is disposed. A refused validation never loads its document. During a replacement's window the standing document and the incoming one are therefore both loaded. A document that a caller validates and never settles, as the suite's direct `assertRenderable` calls do, counts as loaded until the store is next reset. Call **obsolete** the nodes of the store that no loaded document has prepared in the current generation, and O their number.

**Invariant.** At the start of every outermost operation that is not a document load, O < H.

Two facts carry the proof. Ordinary operations prepare only the text of loaded documents (Context, "Nothing else"), so they never increase O; test C is the guard for the paths the corpora reach. A reset makes O zero. What remains is to check every event that makes nodes obsolete. Write N for the store's node count when a check runs.

1. **Successful load, store at H or more at its start.** The load empties the store (O = 0). Validation adds A nodes, all the incoming document's. During the window, operations add only loaded documents' text: the standing document's graph, which it rebuilds if operated, and other viewers' graphs; call that W. At `installed()` the generation is the recorded one and N − A = W. The standing document's nodes become obsolete, so O ≤ W. The check empties the store when W ≥ H; otherwise O ≤ W < H. In the single-viewer case that originates this change, the Enigma's initial mount or any republish with the model idle during asset loading, W is zero: no reset, and no second preparation.
2. **Successful load, store below H at its start.** Nothing is emptied; the load carries C = N < H nodes, which include the standing document's graph. Validation adds A, and the window adds W. At `installed()`, N − A = C + W and O ≤ C + W. The check empties the store when C + W ≥ H; otherwise O < H. A small standing document replaced with nothing operated in the window gives C + W = C < H: no reset.
3. **Refused load, store at H or more at its start.** The load empties the store and prepares a partial graph of P nodes. At its end, N = P: emptied when P ≥ H, otherwise O ≤ P < H. One refused load can raise the generation twice, once per reset.
4. **Refused load, store below H at its start.** The load carries C < H and prepares P. At its end, N = C + P: emptied when C + P ≥ H, otherwise O ≤ N < H. A refused document whose partial graph is as large as a whole document is therefore gone before the last good model's next operation.
5. **Refused after validation.** `abandoned()` empties the store when N ≥ H; otherwise O ≤ N < H.
6. **Disposal that is not the last.** The release empties the store when N ≥ H, at once or at the end of the open scope; otherwise O ≤ N < H. The survivors rebuild their graphs once at their next operations.
7. **Last disposal.** The store is emptied; O = 0 and N = 0, as today.
8. **A load that is not outermost.** It cannot reclaim at its start, so it may carry C ≥ H. Its refusal and its settlement are honoured at the end of the outermost scope, by which time N has only grown: a refused nested load that carried C ≥ H is emptied there (case 4 with C + P ≥ H), and an installed one is emptied by the H + A check (case 2 with C + W ≥ H). The invariant therefore holds by the next outermost operation. The price, one further preparation of the incoming document, is paid only by a nested load that carried H or more, which the viewer never makes.

`installed()` with a generation that moved since the validation (another viewer's load or disposal reset the store in the window) checks N ≥ H instead: everything resident was prepared after that reset, so O ≤ N.

From the invariant, at the start of every outermost operation that is not a load, the store holds fewer than H obsolete nodes plus the graphs of the loaded documents, and an ordinary operation adds only loaded documents' text. A protected load may exceed this while it runs, as today. The bound does not depend on how many loads, refusals or disposals came before.

Every reset still goes through `resetStore()`, which raises the generation by exactly one; every check runs with no scope open; nothing else moves the generation. The rule that no reset happens inside a scope is unchanged.

Under this policy expression text arriving while one document stays mounted is bounded by that document's own text, prepared at most once per generation. No present runtime path composes text after load (Context). If a later change added one, the composed nodes would be the loaded document's own, so they would not break the invariant, but they would grow the store until the next reclamation; test C is the tripwire for the corpora's paths and is not a proof for paths the corpora do not reach.

### 3. Proof: red-first tests at the default configuration, and tests of each reclamation point

Each new test is self-contained, builds synthetic documents in the test, imports no project export and states whether it is red on the base. A wide binding table (`_b0 = x * 2`, `_bi = _b0 + i`) adds two nodes per entry without deep recursion; 66,000 entries give 132,003 nodes, above 125,000. A chained table must not be used: a 45,000-deep chain overflows the evaluator's recursion in a probe, a limit this change does not touch.

- **A. One large document across adjacent operations.** `assertRenderable` the 66,000-entry document at the default configuration, then run three or more separate outermost operations that evaluate an entry through `table.roots()`, plus a `WidgetTree` update of its root. Assert the generation is unchanged, `bindingPreparationMetrics()` stays 1, and values are correct. Probe on the base: each operation changed the generation and re-prepared the table (preparations 2, 3, 4; about 370 ms each on this host).
- **B. Two documents of very different size, alternately.** Load the large document and a small one that uses the same binding names for different expressions. Loading the small one may reclaim the large graph once (Decision 1, point 1). After one operation each, alternate at least three operations on each: no generation change, the large table prepared exactly twice in the whole test (at its load and once after the small document's load emptied the store), and each document's values follow its own bindings. Red on the base for the generation and preparation counts. (Preparation counts are per test through `resetBindingPreparationMetrics()`; the counter is page-wide, so the test reads it around operations on one table at a time.)
- **C. Repeated operation adds nothing.** After load, run each clocked-corpus script twice and advance each running-corpus machine through its scripted ticks, and update a posed tree twice: `expressionMetrics().nodes` after the repeat equals its value after the first pass. This pins Decision 2's claim for the paths the corpora reach. It may be green on the base for small corpora; it is a guard, not the red test.
- **D. History under the production policy.** With H lowered to 5 and `everyOperation` false, load two documents A and B through `assertRenderable`, then 60 times load a replacement of B (settling it `installed()`) and have a refused replacement (`_bad` names itself) refused, evaluating A and the current B between loads. Assert: values correct; no generation change during the operations between loads; at least one generation change per load; and the high-water `peakNodes` is at most (H − 1) + 2g, where g is the largest single-document graph of the test, measured in the test as the `peakNodes` of loading each of its documents, good and refused, alone into an emptied store. Derivation: at the start of an ordinary operation the store holds fewer than H obsolete nodes (the invariant) plus the graphs of the two loaded documents, at most 2g, and an operation adds only their text; inside a load the store starts empty or below H and the load adds at most one document's graph, at most (H − 1) + g. So the high-water is at most (H − 1) + 2g, which replaces the earlier draft's H + 3g. A revision-time experiment (since reverted) with 20-entry wide documents measured g = 45, a bound of 94, a high-water of 82 nodes and 180 generations over the 60 iterations (three resets each: the replacement's start, the refusal's start and the refusal's end); it settled no replacement, and Decision 1 makes an installation with no window growth reclaim nothing (test I). The existing replacement test proves boundedness under constant pressure; this one proves it for the policy that ships.
- **E. A viewer that is not the last is disposed (store interface).** With H lowered to 50 and `everyOperation` false: two `retainExpressions()` holds; a graph of H or more prepared for the first and a 3-node expression for the second; one `releaseExpressions()`; then one ordinary outermost operation that evaluates the survivor's expression. Assert `nodes` is below H plus the survivor's graph, the survivor's value is correct, and the generation rose exactly once across the release and the operation. A second half releases a hold inside an open scope and asserts the generation is unchanged inside the scope and one higher at its end. Experiment: 3 nodes after the operation, one generation.
- **F. A refused load (through `assertRenderable`).** With H lowered to 50 and `everyOperation` false: a 3-entry good document loaded (9 nodes); then a 60-entry document with `_bad = _bad + 1` refused, its partial graph above H; then one ordinary operation on the good document. Same assertions as E. Experiment: 8 nodes after the operation (the good document's table and the entry read), one generation.
- **G. A validated document abandoned.** As F, except that the second document is valid and passes validation, and its `settlement.abandoned()` is called; then a later `installed()` on the same handle changes nothing. Same assertions as E. Experiment: 8 nodes, one generation.
- **H. The replaced graph rebuilt in the window.** With H lowered to 50: a 60-entry document loaded and operated; a 60-entry successor with different expressions validated (its start empties the store: one generation); the standing document operated again, rebuilding its graph of H or more; then the successor's `settlement.installed()`. Assert a second generation rise at the settlement, and that the successor then evaluates correctly. Experiment: two generations in all; the successor evaluated 565.
- **I. An installed large document keeps its graph.** As H, without the standing document's operation in the window: after `installed()`, three operations on the successor cause no binding-table preparation and no generation change after the load's own. This is the guard for "no second preparation at its first operation".

E and F are green on the base, which empties the store at the start of the next operation once it holds H or more; G, H and I use the settlement handle, which the base does not have. None of the five can therefore be shown red on the base. Each is shown red against the implementation with its own reclamation removed, recorded like the spot-checks of task 4.4: E with the release's request removed, F with the refusal's request removed, G and H with the settlement's request removed, and I with `installed()` requesting at H instead of H + A. A revision-time experiment applied the mechanism of Decision 1 (since reverted) and saw exactly that: with the three requests removed, E, F, G and H failed on their node or generation assertions (84 against a bound of 53; 131 and 130 against 59; generation 5 where 6 was expected) while I and D passed; with `installed()` at H, only I failed (one preparation where none was expected).

`expression-lifetime.test.ts`'s existing "retains a current large graph across adjacent operations within finite capacity" (102,700 nodes, below 125,000) remains true and stays as it is; test A is the one that crosses the old line.

The viewer's own settlement calls in `replaceTree` and `manifestChanged` cannot run in this suite, which sets up no DOM or WebGL for `mount()`. Their exits are checked by review of the diff; the reviewer's measurement on the Enigma page (task 6.2) reads the generation across the initial mount, which shows whether its installation reclaimed.

### 4. Memory: what is retained and how it is measured

Retained: the node array, the structural intern map, the string-to-root map, the free-name sets and the memo arrays of the store, for the graphs bounded in Decision 2. Nothing else is newly kept; holders already keep their source text or a getter, and the settlement handle holds two integers.

Order: in a Node probe (`NODE_OPTIONS=--expose-gc`, one forced collection before each reading) the 132,003-node synthetic document held 60.4 MB after validation, of which 24.4 MB stayed after the store was emptied (the document and its table, still referenced): about 270 bytes per node attributable to the store, for that synthetic shape in V8 under Node. Scaled linearly, the Enigma's 546,768 nodes would be of the order of 150 MB. That scaling is an estimate, not a measurement, and the shape of a real graph may differ; the reviewer replaces it with a measurement (below).

Against the base: the base also holds a complete store between operations, because it empties the store only at the start of the next operation and rebuilds it within that operation. The evidence file took one heap reading per run (1,932 and 1,961 MB) and does not record whether it fell between operations or inside one; read between operations, both runs had a full store resident. Their 30 MB difference is therefore not the store's size and must not be quoted as such. What the change removes is one complete rebuild's garbage per operation; between operations it keeps resident what the base already held there.

The applier records: a deterministic node count per test (`expressionMetrics().nodes` and `peakNodes`), and one heap reading per state (loaded, after operations, after final disposal) of the synthetic 132,003-node document, under `NODE_OPTIONS=--expose-gc` run as a single file; the reading is evidence and not asserted. Final disposal returning `nodes` to zero is asserted, as today. The reviewer measures the store's resident size on the Enigma page directly with the probe build of task 6.2: the heap after a forced collection with the store full, and again after the store is emptied through the probe build's `releaseExpressions()`/`retainExpressions()`, the difference being the store's size on that page; it replaces the 150 MB estimate in `evidence.md`.

### 5. Forced reclamation in the suite

`EXPRESSION_LIMITS` gains a boolean, `everyOperation`, default `false`. When it is `true`, every outermost operation, ordinary or load, also empties the store at the start if it holds H or more, as on the base; the reclamation points of Decision 1 stay in force. Each of those points empties the store only when it holds H or more, so it only brings forward, with no operation between, a reset the base would make at the start of the next outermost operation; generation counts read after that next operation are the base's. It is a widget-source export like `EXPRESSION_LIMITS` itself, not on the bundle entry or the handle. Lowering H with `everyOperation` true is the suite's way to reclaim between any two operations; lowering H alone now forces reclamation at the points of Decision 1 only.

A proposal-time experiment applied the policy to the source (reverted) and ran the four files unchanged. Seven tests failed because they assert a reclamation that no longer happens; seven others still passed although they no longer forced any reclamation. A revision-time experiment with the mechanism of Decision 1 (reverted) saw the same failures, plus the late-entry test below. The second group is the danger, so every test that forces pressure, whichever mode it uses, also asserts that `expressionGeneration()` rose during the pressured stretch. Each file's `afterEach` (or the test's `finally`) restores both fields.

`expression-lifetime.test.ts` (each lowers H):

- "reconciles document-local binding changes and poses the new tree under pressure" (5): `everyOperation`; add the generation assertion. It still proves a reconciled tree reads its new table after reclamation.
- "defers reclamation in nested scopes and releases scopes after exceptions" (1): `everyOperation`; its counts (+1 after the throwing operation, +2 after the next) then hold as written. Add the same pair for `withDocumentLoad` with `everyOperation` false: a refused load releases its scope and reclaims at its own end, and a refused load nested in an open scope reclaims only at that scope's end.
- "keeps live documents separate and bounds successful/failed replacement history" (5): `everyOperation` (it failed with 157 > 50 without it). It still proves correctness and bounded history under constant pressure; test D adds the shipping policy.
- "keeps a running bank stable while traversing a kink across generations" (5 against the default): `everyOperation` for the pressured run; assert generations rose in it and did not rise in the default run, which now also shows ticks keep their graph.
- "replays all clocked corpus operations unchanged under pressure" (5): `everyOperation`; assert generations rose in the pressured replay.
- "reconstructs a pose scope acquired before reclamation" (1), "reconstructs a held path with its original standing values" (1), "prepares a multi-entry binding map larger than the threshold coherently" (5), "classifies root plus bindings above the threshold, cold or warm" (5): `everyOperation`; add the generation assertion where the test lacks one.
- "reconstructs retained kink operands when old IDs name DIFFERENT nodes" (1): `everyOperation`; it already asserts the generation rose.

`validation-pressure.test.ts`:

- "prepares one coherent validation graph above finite headroom and reconstructs afterward" (5): split. (a) Shipping policy: after the protected validation, an ordinary operation keeps the generation and leaves `bindingPreparationMetrics()` at 1 (red on the base, which reclaims). (b) `everyOperation`: the following operation reclaims, the generation rises by one, the table re-prepares once and `_b79` is still `3164` with `Object.is`.
- "discards negative facts between document meanings and operations, even when node IDs are reused" (1): loads reclaim under both modes, so it keeps forcing reuse of node ids between validations; add the assertion that the generation rose between the loads.
- "refuses an invalid unreferenced late entry in an oversized table and releases its scope" (5): its one assertion moves. It reads the generation after the refused load and expects the recovery load to raise it; the refused partial graph (above 5 nodes) is now emptied at the refused load's own end, so the recovery load finds the store below 5 and does not reclaim (the revision-time experiment failed it with 26 > 26). Read the generation before the refused load and assert it rose by the time `assertRenderable` has thrown. That reset can only run once the load's scope has closed, so the test still proves the scope was released, and more directly than before; then the recovery load validates and its table evaluates correctly. This is the one existing assertion the change rewrites.

`expressions.test.ts`:

- "drops and rebuilds the table when the node ceiling is passed" (3): `everyOperation`; add a twin with `everyOperation` false in which a plain `prepare` above H does not reclaim and a `withDocumentLoad` does.
- "a held BindingTable re-prepares its roots after a reset, and evaluates correctly" (3): `everyOperation`.
- "the table survives a release while another holder remains" (default H, 3 nodes): unchanged and still green; a release that is not the last reclaims only at H or more.

`run/program.test.ts`:

- "re-prepares from the expression strings after a store reset" (1): `everyOperation`.

Tests that only call `retainExpressions(); releaseExpressions();` to empty the store (`document.test.ts`, `run/run.test.ts` and the files above) are unaffected: the last release still empties the store unconditionally, and "rises on a reset and not otherwise" still sees one generation, because a release's two requests produce one reset.

### 6. Holders that survive a reclamation by generation

The mechanism of a reclamation is unchanged: `resetStore()` empties every node-keyed structure, ids restart from zero, and the generation rises by exactly one; nothing else moves the generation. What changes is where reclamations happen (Decision 1), and every one of them still happens with no scope open, never between two acquisitions or during a walk.

- `bindings.ts`'s `roots()`: re-prepares the whole map inside one scope when the generation moved. It now re-prepares less often; when another viewer's load, settlement or disposal empties the store it rebuilds once.
- `ExpressionPath`: keeps source and standing values and rebuilds its `PathValue` on a generation change; unchanged, and rebuilt less often.
- Kink descriptors from `retainedKinkLevels` (program and clocked loaders): keep source plus postorder index and rebuild operands once per generation; unchanged.
- `validationProfileInspector`: tied to one binding map and one generation inside one validation, and throws if used after the generation moved. The validation is the load operation; its reclamations happen at its start, before the inspector exists, and on refusal at its end, after the scope that held the inspector has closed. A settlement runs after the validation has returned. An inspector can never see a reset. Unchanged.
- Pose-scope binding getters and tree reconciliation, which compare both tables inside one scope: unchanged.
- The settlement handle: holds a generation and a count, never a node id; it reads the generation only to decide which threshold applies.

No holder depends on the store's size, and the generation's contract — rises by exactly one per reset and only then — is unchanged. Decision 1 adds callers of the reset and removes none of the guards.

## Alternatives considered

- **Raise the constant a third time (to 600,000, or 2²⁰).** Rejected: it would fit the Enigma and the Voron by accident and put the same failure in front of the next larger document. The record has twice called a constant provisional.
- **A dynamic ceiling, measuring the live graph from per-mount holds.** Each mount (and each worker session) would hold a measured footprint (distinct nodes reachable from what its validation prepared), and the trigger would become the held total plus headroom. It meets every goal and also spares a large mounted graph when another viewer loads or is disposed. Rejected for now: it needs a holder identity, a reachability walk and wiring through the mount and the worker for a benefit no named project needs. It is what a project that needs more than the stated limit would justify (Risks).
- **A ceiling relative to the size reached at the last load.** Rejected after simulating it. With a large document already loaded, loading a small one empties the store; the floor becomes the small one's size, the large one's rebuild exceeds floor plus headroom, and every operation reclaims again: the same failure, triggered by a second viewer.
- **Arm one size check for the next outermost operation, instead of checking at the event.** Equivalent for disposal and refusal, but it cannot tell a successful installation's incoming graph from obsolete state, so after a large document's installation it would empty the graph that operation is about to need, which is the failure this change removes. The per-event threshold of Decision 1 (H + A at installation) is what avoids that, and it needs the event anyway.
- **Reclaim only at the end of a refused load and leave the replacement window alone.** Rejected: the standing model operates while the incoming document's assets load, so after a load that emptied the store it rebuilds its graph, which becomes obsolete at installation and can be as large as a document; a validated document refused afterwards (a required asset) leaves its whole graph resident. Both make the invariant false.
- **Truncate the store back to the size it had when the incoming validation ended.** Nodes are interned children first, so a prefix of the node array is closed, and truncation would drop exactly the window's growth. Rejected: it is a new kind of reset that the guards would have to treat as a reset anyway (ids beyond the prefix are reallocated), so every holder would rebuild, it prunes three maps by walking them, and it buys nothing the H + A check does not give in the cases that occur.
- **Detect a useless reclamation and stop reclaiming until something changes.** Rejected: it needs the same load events this design uses and adds a heuristic state on top of them.
- **Compaction: rebuild only what live holders reach.** Rejected: live roots would have to be registered with the store, the compaction walk costs a full graph per reclamation and ids still change, so every holder rebuilds anyway.
- **Never reclaim except at final disposal.** Rejected: a development session's republishes, and its refused ones, would accumulate without bound, which the ratified requirement forbids.
- **Per-document stores.** Rejected by ADR-043 and ADR-044 and still rejected: it gives up page-scoped sharing to avoid guards that cost one comparison and one integer.
- **A heap-relative ceiling (`performance.memory`, `navigator.deviceMemory`).** Rejected: Chromium-only or coarse, and nondeterministic for the suite.
- **Hold one scope across a whole press.** Rejected: a press spans animation frames, and a scope never spans an `await` or a frame (ADR-043).
- **Make parsing faster.** Out of scope, and it would only make the needless work cheaper.

## Risks / Trade-offs

- [A large graph stays resident while it is loaded] → It is resident today between operations as well (Decision 4); the applier measures node counts and heap, the reviewer measures the store's size on the page; final disposal still empties the store.
- [Stated limit: another viewer's events empty a large mounted graph] → One viewer's document load, its settlement when the window grew by H or more, or its disposal empties the whole store when it holds H or more, and a large graph in another viewer then rebuilds once at its next operation: once per load (twice when the large graph was operated during that load's asset window and so counted as window growth), once per disposal. This is no worse than the base, which rebuilt it at every operation, and no named project mounts a large document beside a second viewer. A project that needs a large graph spared from another viewer's events would justify the per-mount accounting alternative; nothing in this change forecloses it.
- [A republish of the same large document re-parses it at the load] → Unchanged from the base: the load finds the store at H or more and empties it before validation.
- [A replacement whose window grew by H or more is prepared twice] → The installation empties the store and the incoming document rebuilds at its first operation. It requires the standing model, or another viewer, to prepare H or more nodes the incoming document does not share while the assets load; the base paid that preparation at every operation.
- [The viewer's settlement calls are not exercised by the suite] → `mount()` needs a DOM and WebGL the suite does not set up. The store's side of every settlement is tested (G, H, I); the viewer's exits are checked in review of the diff; the reviewer's page measurement reads the generation across the initial mount (task 6.2).
- [A future path that composes expression text per operation would grow the store until the next reclamation] → Test C pins the corpora's paths; Decision 2 records the invariant the policy relies on so a later change that breaks it is visible in review.
- [Pressure tests silently stop testing reclamation] → Every forced-pressure test asserts that a reclamation happened (Decision 5).
- [The experimental figures come from Node, not Chromium] → They choose the test shapes and the order of magnitude only; the Enigma page measurement is the reviewer's acceptance (task 6.2).
