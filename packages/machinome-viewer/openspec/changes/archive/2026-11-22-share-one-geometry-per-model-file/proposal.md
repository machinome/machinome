## Why

One open copy of the Enigma I page (`enigma-i` at `081f4e6`, viewer at framework `4b456edf`) is 4,214 MiB in Chromium, and 3,207 MiB of it is the model's triangles held twice: 1,603 MiB of typed arrays in the tab and the same bytes again as WebGL buffers (`workflow/evidence/enigma-page-memory-2026-11-22.md`; `workflow/warts.md`, "Every part has its own geometry and material, and an idle page draws all of it every frame", its last two entries). The 2,868 parts read from model files are 1,110 MiB of each 1,603, and they name 993 files: 16.2 million triangles are held where 7.8 million are distinct, because every part parses the file it names into a geometry of its own (`geometry-admission.ts` 73: "Each subscriber starts its OWN STLLoader parse"). The file is fetched once a page load; it is parsed once a part. One geometry a file would hold 573.5 MiB less in each process. The first requirement of this change is that no part ever shows a geometry that has been freed and no part is given older bytes than it is given today; the second is the memory.

## What Changes

- **One reading, one geometry.** A reading of a model file is one request and one parse of its response, with the normals computed once. Within one viewer, every part and marking that asks for the same file while that reading is open is drawn from its one geometry: one set of typed arrays in the tab, one set of buffers in the viewer's graphics context. At a mount every part asks before any load settles (the tree is built synchronously), so on the Enigma's built page every part naming one file shares one geometry.
- **When a reading is open.** A reading is the group of loads ADR-078 already lets share one request: it is joined only while its request has not settled, and never after. A reading never outlives its request: there is no cache, and no part joins a geometry already on screen. The viewer reads no new signal for this; the rule reads the URL, whether a reading of it is open, and which viewer asks.
- **Freshness is the base's.** A part is given the bytes it is given today. On the base, an update asking for a file whose request is still in flight receives that request's bytes, because three.js 0.156.1's `FileLoader` folds overlapping requests for one URL; here it joins the reading and receives the same bytes as the same geometry. Measured for this proposal with three.js's own loader, in the widget suite and in Chromium: two artifact notices for one path, the second sent after the file was rewritten while the first request was held, leave the part showing the first notice's bytes. That staleness is the base's, is not this change's subject, and is recorded as a finding of its own (`workflow/warts.md`, "An update that asks for a file still being fetched is given the earlier request's bytes").
- **A count of holders, not a cache.** Each part holds a share and releases it exactly once, however many times its cleanup runs. A geometry is freed in the tab and in WebGL when its last holder is replaced, removed or disposed and no subscriber is still waiting on its reading, never while a mesh in a scene shows it; a reading that every waiting part abandoned is freed on arrival, never uploaded. A marking lifts its decal from a copy as today and lets go of the file's geometry at once.
- **Per viewer.** Two viewers in one page never hold one geometry: the requests of one admission group are still one request, and the parse is handed to the first viewer and copied for each further one, so disposing a viewer frees everything it held. three.js keeps a renderer's buffers and a listener on every geometry it drew until that geometry is disposed, and `WebGLRenderer.dispose()` frees neither (read in 0.156.1), so one geometry held across viewers would keep a disposed viewer's buffers and context alive.
- **Nothing else moves.** The swap stays: an update's geometries are prepared while the old stay on screen and swapped in one step. The admission budget, its FIFO order, queued work cancelled without a request, readiness, the last good model after a failure, the order of drawing, the picture, picking, bounds, highlights, markings, flexible parts, the `on-demand` mode, viewer API 30 and document versions 1 to 14 do not change. A development session pays a second copy where a republish adds a part naming a file already on screen.
- Tests red on the base: in the widget suite, the real tree with three.js's real STL loader and `FileLoader` over a stubbed network, counting requests, parses, geometries, holders and disposals, and the bytes each part shows; the real viewer in jsdom for reloads, two viewers and the handle's updates; a generated-sequence proof with a detector after every step; mutations for every rule; in a real browser, the WebGL buffers created and deleted across a mount, a changed file and a disposal, and pixels against the same document with every part naming its own copy of the bytes.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `viewer-package`: a new requirement, "Parts that name one model file share one geometry", states the sharing, when a reading may be joined, the release, and that two viewers never share. The requirement "Fresh mounts draw loaded rigid assets independently of fetch completion order" is restated: its scenario "Repeated paths retain separate part ownership" promises that "each part still owns separate geometry" and now says each part holds its own share of one geometry; its failure and disposal sentences say a returned geometry is released, and freed when no other part holds it, where they said it is disposed. Design Decision 9 lists every sentence read and why the others hold.
